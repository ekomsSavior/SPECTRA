1. Turn a promising lead into a repeatable investigation

This manual assumes you can identify a file, distinguish a VA from a file offset, follow a reference, read a simple loop, and save an investigation. We will now work on the difficult middle: imperfect metadata, ambiguous control flow, missing state, competing types, and results that change when your assumptions change.

Keep the beginner manual nearby for control definitions. This book uses SPECTRA 0.18 and the same benign practice pack. The objective is a defensible research workflow that stays in the browser wherever the current engines support it. Full operating systems, native host-process attachment, managed execution, and arbitrary device emulation are not implied by an engine dropdown.

Define the experiment before the setup

Replace “run the binary” with a contract: “At entry E, with ABI A, memory M, arguments I, and modeled services S, does this routine produce O before stop condition T?” This describes what can be reproduced. It also exposes the missing inputs before you spend an hour clicking Continue.

Artifact: exact SHA-256 and provenance
Entry: VA, function boundary evidence, load bias
Inputs: arguments, buffers, registers, globals
Environment: model, dependencies, hooks, virtual files
Prediction: output bytes, return, or branch outcome
Stop: return / exit / breakpoint / budget / fault
Observation: actual output and retained evidence
Residual uncertainty: what this setup cannot establish

Separate four levels of confidence

Stored fact: a byte range and hash. Recovered relationship: an instruction points at a string or target under the selected mapping. Analyst interpretation: this appears to be a record parser. Observed model behavior: the parser returned a particular value for supplied bytes. Each layer builds on earlier evidence but can introduce assumptions.

Use names to organize, not to erase uncertainty. parse_record_candidate is useful when you have two loads and a comparison. Rename to validate_record_header after callers and failure paths support that role. Preserve rejected hypotheses if they explain a consequential decision.

Choose a stopping rule

An intermediate analyst should be able to stop without “understanding everything.” For a decoder, the finish line may be a reproduced output with source range and parameters. For a patch review, it may be a confirmed changed condition plus its covered callers. For a client method, it may be an invocation recipe with explicit dependencies and untested server semantics.

Exercise: Rewrite “this binary encrypts data” as a testable question. One answer is: “Does function F transform the 32-byte supplied buffer into the predicted output when given key K and IV V under this ABI?” That tests a specific transformation. Identifying an algorithm or security property needs additional evidence.

2. Loader reasoning and ARM static PIE

A wrong mapping can make correct bytes tell the wrong story. Verify where file bytes become memory, which regions are zero-filled, where execution begins, and who applies relocations. For ELF, program headers describe loading; p_filesz and p_memsz can differ, with the extra loadable memory initialized to zero. The ELF program-loading specification defines these relationships. SPECTRA supports a selected subset rather than every ELF configuration.

Case file: watch a pointer relocate

  1. Save your case. In Debugger lab choose ARM32 and Load ARM PIE demo.
  2. Choose Use detected setup and inspect the load check, relocated entry, and relocation count.
  3. Under Load base, raw bytes & session assumptions, verify the default ARM PIE load bias 0x10000000 and Program startup relocation ownership.
  4. Initialize. Read four bytes at VA 0x10001000. Expect the little-endian word 0x1020 before startup relocation.
  5. Add a four-byte write watchpoint there, run, and inspect the write. Expect 0x10001020 after startup adds the bias.
  6. Remove the watchpoint and continue. The benign fixture writes “pie” to captured stdout and exits zero.

The arithmetic matters: 0x1020 + 0x10000000 = 0x10001020. The location of the pointer is 0x10001000; the value stored there points somewhere else. Record both. A screenshot showing one address without saying which role it has loses the key fact.

Relocation has an owner

In Program startup mode, SPECTRA maps the admitted static PIE but lets its startup routine adjust pointers. The alternative Debugger applies REL · alternate entry applies supported relative relocations before execution and requires a different start address. It is for a justified alternate-entry experiment, not a shortcut that performs all initialization.

If you apply relocations first and then re-enter a self-relocator, the bias may be added twice. Conversely, starting after initialization without supplying its effects can leave stale pointers. Constructors, global state, TLS, and argument context are separate from relocation. Passing one loader check does not supply them all.

Change the bias carefully

As a controlled follow-up, choose another aligned, non-overlapping load bias accepted by preflight, keep Program startup ownership, and initialize again. Recompute the watched location as bias + 0x1000 and predict the target as bias + 0x1020. Save both recipes and outputs. Do not reuse a breakpoint at the old loaded address.

The current ARM/Thumb path admits little-endian EABI5 static PIE with bounded local R_ARM_RELATIVE records and no required external interpreter/shared libraries. Unsupported relocation kinds remain blockers. This is not general dynamic linking or AArch64/x64 PIE support.

File-to-VA verification

For a file-backed load segment, a local mapping is VA = segment VA + (file offset - segment offset) + load bias. Apply it only within that segment's file-backed interval. The reverse mapping can fail for BSS or newly allocated memory. State the segment and bias with every derived address.

Deliverable: a before/after memory capture, relocation ownership, bias, pointer-storage address, pointer value, stop reason, and a sentence explaining why two distinct addresses are involved.

Use the ledger as a falsifiable conversion

File structure → Address mapping ledger performs exact unsigned 64-bit conversions for declared PE, ELF and thin Mach-O regions, the current raw range and captured debugger mappings. Extended ELF program-header numbering (PN_XNUM) is supported in the mapping parser. That parser capability is separate from loader admission in a particular debugger architecture.

Choose the mapping source and coordinate type explicitly. Resolve a known byte, inspect its original bytes when available and reverse the conversion. Preserve overlapping candidates instead of selecting a convenient unique answer. Test both the last file-backed byte and the first zero-filled byte in a segment: that boundary catches formulas applied beyond their valid span.

For recorded allocation or rebasing, use event-order mapping history, not merely the final captured map. For compressed children, retain the parent-member transformation rather than claiming a simple offset relationship. A recorded map is structural evidence; it is not a complete memory-content history.

3. Indirect calls, switches, and honest coverage

Direct branches encode enough information to recover a target easily. Indirect transfers obtain a destination through a register or memory. That may represent an import, callback, virtual method, jump table, or ordinary function pointer. The difficult part is following how the value was produced and whether it can change.

Use the analysis demo as your reference specimen

  1. Save and choose Load analysis demo in Disassembly. Let Analyze code finish.
  2. Find the dispatch routine and open Indirect targets & switch tables.
  3. Inspect the guard before the dispatch. Determine the admitted input range and default path.
  4. Expand the recovered table. For each of the three cases, record the label, entry VA/file offset, raw stored value, and resolved target.
  5. Verify at least one entry in Hex, then follow its target in code. Compare the Blocks edges and Cross-references switch entries.

Absolute versus relative entries

An absolute table entry contains a target value directly. A signed-relative entry contains a displacement that must be added to the specified base. As a separate arithmetic example, a 32-bit entry f0 ff ff ff interpreted as signed little-endian is -16. With relative base 0x2000, the target is 0x1ff0. Treating it as unsigned gives a nonsense distant target.

The base is part of the compiler's scheme; it is not always the entry address or instruction PC. Check the actual address-building instructions. A guard using an unsigned comparison can bound a table; a nearby signed comparison is not interchangeable. Case labels can begin at a nonzero value after subtraction.

Supply a hypothesis only when you can defend it

Select the dispatch instruction, choose Use selected instruction, and enter a target plus a note, or supply table VA, count, width, encoding, relative base, and first label. Before saving, calculate one entry by hand and check that all proposed targets fit aligned mapped code. Tables are capped at 256 entries.

Save the hypothesis, inspect the new static edges, then remove it once to compare the result without your contribution. This teaches which information came from the file and which you supplied. Hypotheses can extend static discovery. They do not patch memory, install debugger hooks, or automatically change Ghidra's internal control flow.

What automatic propagation really knows

SPECTRA follows selected x86/x64 and AArch64 address-building sequences inside a basic block. Calls, joins, and unsupported operations discard facts. A read from a writable slot is a candidate because runtime writes can change it. Mixed ARM/Thumb transitions and other register-built targets can remain unresolved.

Increasing the instruction budget answers a coverage question, not a precision question. Continue analysis may discover more reachable bytes while leaving the same unresolved dispatch. Conversely, one justified target hypothesis can expose a function without decoding megabytes of unrelated content.

Report the boundary

Record the analysis budget, partial/finished queue status, unresolved transfer count, and any analyst edges. “No callers found” means no callers found by this pass. “Observed case 2 under input 2” is a runtime statement only after an actual modeled run.

Exercise: What evidence would distinguish a jump table from an array of ordinary data pointers? Answer: A bounded index, compatible entry interpretation, executable targets, and an instruction sequence that transfers control through the loaded value. A row of pointer-looking numbers alone is insufficient.

4. Recognize library work without erasing application logic

Library recognition saves time by separating common support routines from the behavior you came to study. It can also mislead if a familiar name gets attached too confidently. SPECTRA distinguishes declared imports, forwarding thunks, and exact-byte reference candidates. Preserve that distinction in your notes.

Three different kinds of evidence

  • Declared import: the file asks for a named external symbol. That names an interface, not necessarily the runtime implementation it receives.
  • Import-forwarding thunk: a small routine transfers through a recognized slot. Inspect whether it changes arguments or state before forwarding.
  • Exact function bytes: the recovered contiguous bytes match a reviewed corpus entry. This is evidence about those bytes and boundaries, not proof of original source authorship.

The starter corpus contains 30 x86/x64 builds of small Church memory/string implementations. It is not a comprehensive libc, Windows, or firmware library database. Compiler versions, optimization, relocations, and boundary differences can defeat an exact match even when the high-level work is similar.

Case exercise

  1. Load the analysis demo and open Functions.
  2. Inspect library-function evidence for one candidate. Read the source/basis and any competing names.
  3. Open its instructions. Identify its argument use, loop or copy/compare behavior, and return.
  4. Use Use this name only when you accept the evidence. Check the resulting Notebook entry.
  5. Return to a caller. Ask what the application passes to this routine, rather than spending all your time on the common helper.

Build a small reviewed signature pack

Select a well-understood contiguous function of 16-4096 bytes, give it a precise name, and choose Export selected function signature. Keep its source/build recipe and provenance with the pack. Import it into another investigation and inspect the match evidence. Current packs are bounded to 512 entries and 256 KiB of signature bytes; they do not run scripts or wildcard rules.

A pack should not silently turn “looks like memcpy” into an official library identity. Preserve ambiguity when two entries share bytes. Different names can compile to identical simple routines. A false name can contaminate later type and behavior assumptions more than leaving a generated address name.

Use absence properly

No match means the corpus did not establish a match under this recovery. It does not mean custom code, malware, or a novel algorithm. An import named memcpy can also be wrapped or replaced at runtime. Combine recognition with call-site evidence and the actual question.

Deliverable: one recognition decision with byte/boundary evidence, one caller explanation, and one sentence stating what the signature does not establish. Reconstruct affected code after a rename; stale output may still carry the old interpretation.

5. Recover structures and propagate useful corrections

Repeated loads from a base pointer at fixed offsets often suggest a record or object. A type turns those offsets into a working layout. It should explain the observed accesses, widths, alignment, and callers, not merely make the output pretty.

Case file: sixteen bytes with a layout

Open companion record.bin. Its exact bytes are:

53 50 45 43  03 00 00 00  10 00 00 00  00 00 00 00
magic        count        payload_size  reserved

This is synthetic teaching data. The field names are supplied by the exercise; in a real investigation they would begin as hypotheses. We will use little-endian 32-bit values for count, size, and reserved.

  1. Open Decompile's Structure workspace. Select x86-64, little endian. Under Raw firmware mapping, enable a raw range with offset 0, length 16, load VA 0x1000, and function VA 0x1000 so the layout has a native language context. These bytes are data: do not decompile or execute them as instructions.
  2. Set Structure name to TrainingRecord and Total byte size to 16.
  3. Edit/remove the starter rows as needed, then add a char field at offset 0 named magic with count 4.
  4. Add uint32_t fields at offsets 4, 8, and 12 named count, payload_size, and reserved, each with count 1.
  5. Save structure. Set Preview at file offset to 0 and choose Read fields from file.
  6. Expect magic's byte values 83, 80, 69, 67; count 3; payload_size 16; reserved 0. The preview may show numeric char values rather than spelling SPEC.

From layout to a function hypothesis

struct TrainingRecord {
    char magic[4];
    uint32_t count;
    uint32_t payload_size;
    uint32_t reserved;
};

If a routine reads 32 bits at pointer+4 and compares the value with a bound, this layout offers one explanation. To justify it, find callers constructing the same region, other field accesses, and where the alleged length is used. A count and a byte size can share the same integer type while expressing different units.

When applying a type to an actual native function, use Tell Ghidra the types you know, supply a matching declaration/signature, enable Apply and save this function's assumptions, and decompile again. Compare before/after output and inspect warnings. Saved declarations/signatures inform compatible callers in the same language profile; they do not apply across arbitrary CPUs or ABIs.

Do not conflate the correction channels

Address names follow supported views. Notebook signature hypotheses remain annotations until applied through the decompiler controls. Variable/type notes do not rename Ghidra locals. Static indirect-target hypotheses do not force Ghidra edges. Debugger patches do not modify the original file. These boundaries matter when two panels seem to disagree.

Packing, alignment, and pointer fields

The visual layout editor requires ordered, naturally aligned, non-overlapping fields within a size compatible with their alignment. Packed layouts, nested structures, and bitfields need manual C declarations where supported. The file preview does not dereference pointers. A plausible pointer value is not permission to read beyond the selected artifact.

Exercise: A field at offset 4 is loaded with a byte instruction, while your layout says uint32_t. What next? Answer: Inspect neighboring accesses and the consumer. It may read one byte of a larger field, or the hypothesis may be wrong. Do not “fix” the instruction interpretation solely to preserve your type.

6. Call a native routine with a controlled contract

A function harness supplies enough calling context to ask a small question without reproducing an entire application. It does not infer missing object state, initialize every global, or invent dependent services. First inspect a real caller: argument placement, widths, pointers, lengths, and any setup before the call.

Case file: choose a path

  1. Choose Load function + batch demo in Debugger lab. It supplies x64 raw code at 0x1000 with System V x64 arguments 2 and 3.
  2. Inspect the raw bytes and decompile the function. Its intended expression is left ? left + right : right.
  3. Read the prepared argument registers and run to a clean return. Expect 5.
  4. Reset and use Step instruction to observe the test and conditional jump. Locate where zero and nonzero inputs diverge.
  5. Save a baseline checkpoint and the recipe before changing input.

The ABI form supports single machine-word integer/pointer arguments for System V x64, Windows x64, x86 cdecl/stdcall, ARM/Thumb AAPCS32, and AArch64 AAPCS64. Floating-point, aggregates, varargs, multiword values, and hidden object/result conventions are not inferred. RISC-V and MIPS currently require explicit register/stack setup.

Argument locations you should verify

ProfileInitial integer/pointer positionsSimple return
System V x64RDI, RSI, RDX, RCX, R8, R9RAX
Windows x64RCX, RDX, R8, R9; reserved stack areaRAX
ARM/ThumbR0-R3R0

x86 cdecl/stdcallStack argumentsEAX

Consult the AMD64 psABI, Microsoft x64 rules, and AAPCS64 when an actual signature exceeds these simple examples. The form's supported subset is smaller than those standards.

Use a real buffer for a pointer

In Arguments, an entry such as {"buffer":"input"} supplies a mapped pointer, not the buffer contents as an integer. Put this in the two separate input fields:

Arguments:
[{"buffer":"input"},"3"]

Input / output buffers:
[{"name":"input","hex":"41424300","size":32}]

This creates ABC followed by a zero and padding. Use it only for a routine whose signature expects that pointer and length. It is not the right input for the arithmetic demo. The explicit size gives readable/writable capacity; it does not prove the routine will respect a supplied length.

Apply edits at the right time

Initialize uses the current setup editors. Reset repeats the last initialized setup. Register overrides apply after argument preparation and can replace a value you thought the ABI form supplied. Before a confusing run, inspect both the recipe and actual registers.

In Windows function-entry mode, the model retains mapped data and imports but skips execution of TLS callbacks and process/DLL entry. A function that expects their side effects needs additional justified state. Record that omission rather than attributing its fault to the original program.

Deliverable: a completed return for the demo, a documented branch address, and a caller-state checklist for one routine of your own. A faulting run can still inform the checklist; do not present its return register as a completed result.

7. Batches, watchpoints, checkpoints, and negative controls

One successful input can hide a wrong model. Use related cases that discriminate between explanations. A negative control is an input expected not to produce the effect. A boundary case tests the transition where behavior should change. Neither requires a huge random test set.

Run the prepared batch

The function demo prepares zero, two, and seven as the left argument, with right fixed at three. Choose Run cases. Expect clean returns 3, 5, and 10. The zero case uses the alternative path; the other two share the nonzero path. Inspect the observed locations/transitions rather than inferring path coverage from the result alone.

[
  {"label":"zero", "arguments":["0","3"]},
  {"label":"two", "arguments":["2","3"]},
  {"label":"seven", "arguments":["7","3"]}
]

Each case starts fresh. Interactive register edits, memory patches, breakpoints, and watchpoints are not inherited. A case replaces collections such as buffers or hooks with its override; register overrides merge by name. Read the resulting setup if you expected an inherited item to remain.

Interpret the report correctly

The baseline is the first case whose setup succeeded. A faulting baseline remains faulting, so added/missing locations relative to it can be misleading without stop reasons. A report's observed coverage is bounded; it is not a percentage of the whole binary or proof that unvisited paths are unreachable.

Select a case to inspect its buffers and modeled output. Clicking a coverage location can read bytes from the current interactive session, which may differ from that case. A batch report is stored evidence, not a live restored emulator. Use Show interactive result to make the context explicit.

Catch the first meaningful divergence

  1. Predict a branch or output-buffer write that should differ between two inputs.
  2. Prepare the first input interactively, initialize, and set a focused breakpoint/watchpoint.
  3. Run to the stop, capture relevant state, and save a checkpoint.
  4. Initialize the second input and repeat the same observation.
  5. Compare the immediate causes: argument value, flag, loaded field, or modeled service result. Do not stop at “the final outputs differ.”

Replay is a test too

Save up to eight named checkpoints. Restore by replay executes recorded attempts/edits in a fresh emulator and verifies state. It requires the same sample and engine fingerprint. Compare & export reports registers, memory digests/permissions, and applicable model state. A checkpoint from another engine build is not made compatible by relabeling it.

Limits include 16 batch cases, up to 10,000 instructions per case, and 30 seconds overall. Pause/cancel should leave the previous complete report available; an incomplete attempt is not a new complete result. Trace and event retention are also bounded. Choose breakpoints to preserve the evidence you actually need.

Exercise: Two cases both return 5. Are their paths identical? Answer: Not necessarily. Inspect coverage, intermediate state, side effects, and stop reasons. Equal outputs can conceal different work or failures.

8. Verified history: reason backward within a bounded routine

Routine history is useful when the question concerns a specific state transition: which attempted instruction wrote a field, which analyst edit changed a branch, or what the buffer contained immediately before an access. The current mode is deliberately narrower than full process time travel: x86/x64, Bare routine, bounded mapped memory and a finite action log.

Construct a reproducible origin

Initialize from known sample bytes and a documented routine setup. Choose Start history before any step or register/memory edit. Include the ABI, entry, argument buffers and intended return boundary in your note. If the mode rejects the setup, use the ordinary debugger with a recording; a different CPU or process environment cannot become supported by changing a label.

Use the decoding demo as a controlled first experiment. Choose a 512-action budget, identify the output range, and predict the first store from the loaded byte and XOR key. Step until the store occurs. Record the action boundary, instruction address, before/after register values and output byte. Now inspect the immediately preceding boundary and compare your prediction with both states.

What makes a seek a check rather than a picture?

A seek reconstructs state in a fresh emulator from the initial state and recorded actions, then verifies the expected state digest. It does not just paint old register text over the current machine. Read verification failures as failures: do not cite a requested boundary as successfully reconstructed unless the seek completed. Replay can be expensive because each seek starts from the origin; periodic checkpoint acceleration is not implied.

Past state is read-only. Return to latest preserves the live experiment you left. Editing an arbitrary past point into a new branch is outside this mode. To compare a different input, create another documented experiment instead of describing a historical inspection as a new execution branch.

Action boundaries and faults

A timeline action can be an analyst edit or an instruction attempt. The action count is therefore not necessarily the count of successful CPU instructions. A failed attempt may have partial effects; retain the fault, boundary and state change as a unit. An edit is an input to the experiment, not a recovered fact about the original program.

Reverse to breakpoint / access searches recorded dynamic evidence. For a write query, verify that the returned boundary precedes the relevant write; inspect the next action to see its result. An absent access can mean it did not occur in the captured span, or that per-action access capture was clipped. The limit is 128 captured accesses per action. Do not turn absent retained evidence into a proof that an instruction never accesses the region.

Design the smallest distinguishing test

  1. State two competing explanations: the first store uses the current key, or it uses the updated key.
  2. Choose an input for which those keys differ and where the output location is easy to identify.
  3. Capture from initialization, step through the load/XOR/store/update sequence and inspect the boundary before the store.
  4. Track both the input byte and key width. Confirm which value reaches the store; then inspect the key update separately.
  5. Save a concise evidence note with boundaries and addresses. Include your controlled input and any supplied memory, not just the winning explanation.

This is a general method for stack strings, field initialization and small transformations. It is more informative than running until readable text appears, because it establishes a causal relation for a particular operation.

Persistence and capacity are part of the result

The maximum mapped memory is 2 MiB; action options reach 2,048 with a 4 MiB metadata bound. Budget exhaustion stops before the next action instead of evicting the beginning. The history remains session-local. Project/evidence export can preserve a selected state through supported checkpoint replay, but it does not serialize the complete routine-history timeline. Imported traces are not a substitute.

Windows/Linux process models, ARM-family, RISC-V and MIPS history remain outside this implementation. Persistent observation recording is a different mode with different capacity and restoration semantics. Stop or discard the active mode before starting the other; they do not capture simultaneously. Specify which mode produced each artifact in your handoff; “debugger trace” is too vague when one file contains observations and another represents a replayable state.

9. Trace provenance, persistent segments and event alignment

A trace answers a question only within its capture contract. Begin with image identity, environment, initial inputs, recorder/engine version, capture start, ordering, budget and completion state. These determine whether an apparent missing event is useful evidence or simply unobserved history.

Choose the artifact format deliberately

ArtifactInterpretation
Compact trace v1Checksum-validated bounded observation export; latest 200 instruction records, bounded model channels and final mappings. Two read-only import slots. No emulator initialization.
Persistent recording v2Ordered observations saved in incremental local segments, with mapping changes and explicit budgets. Incremental NDJSON export requires a completion footer.
Checkpoint / routine historyState reconstruction under the supported replay contract. It is not conferred on arbitrary imported observation files.

Capture a controlled pair

  1. Choose a short benign routine or supported process exercise. Save the setup and initial input. Initialize, then Start recording before execution.
  2. Use a small byte budget first; available choices are 2, 8, 32 and 64 MiB. The recorder also bounds instruction records at 100,000 and total records at 250,000.
  3. Run to a meaningful stop, inspect partial/fault status and choose Stop recording to flush the final segment. Record whether the run completed or only capture stopped.
  4. Export and save the completed file. Confirm the final completion status. Repeat with exactly one changed input, using a fresh initialization.
  5. Open both for inspection. Compare engine/sample identities and supplied inputs before comparing their events. A changed image or profile is another independent variable.

Persistent segments preserve order across their boundaries; page navigation is presentation, not a new execution epoch. The viewer pages 100 rows at a time. A missing or interrupted tail must remain identifiable. Recovery of completed segments after a killed tab cannot manufacture the last unfinished one. IndexedDB is local persistence, not a durable archival guarantee.

From address lists to mapping history

A memory location can change meaning as mappings are added, removed or rebased. Inspect mapping-change records in event order and use the mapping applicable to the observation. The final map alone may not explain an earlier event. For file-backed regions, retain source offsets and sample identity; for allocated or zero-filled memory, retain the fact that no original byte exists.

Mapping history is not a complete memory snapshot at every event. A record that a region exists does not establish its entire byte content. Likewise, a file offset conversion does not prove that code actually executed at that VA. Keep structural, observed and reconstructed evidence separate in the report.

Read-only imports and external adapters

The supported external adapters include uncompressed x64dbg trace-file version 1 for trace32/trace64 and a bounded Chrome trace JSON import (8 MiB input cap). These formats provide different kinds of observations. An event-duration trace is not a register-by-register CPU recording. Unsupported variants should fail or retain explicit limitations; do not edit a format header to force acceptance.

Imported evidence retains its provenance and unverified status. A checksum is not an author signature and cannot validate a claimed execution environment. If the engine or sample differs from your open investigation, retain the mismatch. Address navigation is justified only with a matching artifact and mapping; the fact that an address lies within some open file is not enough.

Alignment is a proposal

Retained-order comparison aligns row order. Event-aligned comparison can accommodate a short extra path before a shared event, using bounded lookahead. Current alignment is limited to 24 lookahead records, 2,000 rows and 4 MiB of comparison data. Examine skipped/unmatched spans and distinguish a truncated comparison from a fully compared input.

Two equal event labels can hide different parameters, writes or model responses. Repeated events can produce more than one plausible match. Use aligned rows to formulate a candidate divergence, then inspect operands and earlier conditions. Do not report a semantic equivalence result from this UI.

Export failures are evidence-management events

A complete persistent-recording stream has its required footer. Interrupted output should remain visibly incomplete; an extension change or copied footer cannot repair missing records. When retrying, identify which saved recording is the source and which export is complete. After successful download, retain its digest and provenance alongside your report.

For a colleague's trace, a defensible sentence is: “This imported recording reports a write to this mapped region after the listed event; I have not independently replayed the sample.” For your own controlled experiment, specify the supplied input and model. Neither sentence needs to pretend the observation describes every possible execution.

10. Windows recipes: supply state without inventing reality

When a routine expects a clock, configuration file, or service response, an explicit model can isolate the part you want to study. The essential rule is to label what you supplied. A controlled response is evidence about the downstream code under that response, not about the real service's behavior.

Case file: the clock is an input

  1. Load the x64 Windows demo and run its unmodified setup once. Save relevant API events and output.
  2. Open Environment recipe · mapped memory, API hooks, virtual files and ARM MMIO.
  3. Supply the recipe below, initialize again, and run the same entry.
  4. Find the event marked as an analyst hook. Confirm the fixed result and compare downstream behavior with the baseline.
{
  "label":"Fixed clock for a repeatable experiment",
  "hooks":[{
    "api":"kernel32.dll!GetTickCount",
    "abi":"win64",
    "argc":0,
    "result":"1234",
    "label":"Analyst-supplied clock value"
  }]
}

This hook replaces the selected call boundary; it does not change Windows or establish real timing. The benign demo does not branch on the clock value, so identical final output is expected. That is a useful negative control: you can confirm the hook occurred without claiming an output effect that the code never expresses.

Virtual files and memory

A recipe file such as {"path":"C:\\config.txt","hex":"746573740a"} makes recorded bytes available under a modeled path. It does not read a same-named host file. Importing a local file into the virtual-input builder copies selected bytes into a recipe; editing the recipe requires Initialize to affect a new session.

{

12. ARM MMIO and portable hardware reasoning

Firmware often reads an address that stands for a peripheral register rather than ordinary RAM. That is memory-mapped I/O, or MMIO. A read may acknowledge an event, consume a FIFO entry, or expose a changing status bit. Supplying a fixed RAM page can therefore misrepresent the device.

Case file: read 41, write 42

  1. Save and choose Load ARM register demo. The ARM routine reads a word through R0, increments it, writes it back, and returns.
  2. Inspect the function harness: AAPCS32 with argument 0x20000000.
  3. Inspect the MMIO recipe: width 4, one supplied read value 41, and captured writes.
  4. Run to return, then open Recipe, Linux and hardware events.
  5. Expect one supplied read of 41 and a captured write of 42. The bytes/instructions explain why.
  6. Run the prepared cases for 41 and 99. Expect captured writes 42 and 100 respectively.
{
  "mmio":[{
    "address":"0x20000000", "width":4,
    "values":["0","1"],
    "onExhaustion":"stop", "write":"capture",
    "label":"Recorded status sequence"
  }]
}

This second recipe illustrates a two-read sequence. The demo itself reads only once, so it would consume 0 and write 1; it does not demonstrate a polling loop. To study a real loop, use a routine whose instructions actually repeat the read and record why the chosen sequence represents a useful device scenario.

Why exhaustion matters

After the supplied values are consumed, stop is an honest boundary. Explicit hold repeats the final value and can sustain a polling loop, but that is another assumption. Captured writes do not automatically alter future read values or trigger peripheral behavior. A write of 42 is a recorded event, not proof that a simulated device now contains 42.

The model admits exact aligned 1-, 2-, or 4-byte accesses for ARM/Thumb/AArch64. Wrong widths, unknown addresses, forbidden writes, or exhausted sequences stop. MMIO pages cannot overlap ordinary mappings and this recipe mode is separate from the Linux process profile.

Other CPUs

The Training ground hardware exercise also offers RISC-V and MIPS. RISC-V's supplied compressed-instruction addition returns 5 for A0=2 and A1=3. The MIPS fixture returns 6 because its return delay slot adds one. These are tested integer routine profiles, not all ISA extensions or devices.

A MIPS branch/delay-slot pair is handled as an atomic supported step here. A breakpoint on the delay slot sees pre-pair state before the pair executes. If your mental model assumes every Step instruction corresponds to one displayed row, this detail can make the trace seem wrong.

RISC-V ABI distinctions and extensions matter; consult the RISC-V psABI specification when selecting a real target. An ELF metadata mismatch is a reason to investigate, not reflexively accept the override. Likewise, microMIPS, MIPS16, R6, n32, ARM BE8, and arbitrary FP/SIMD behavior are not covered by selecting an ordinary profile.

Missing board behavior

No timing, DMA, interrupt controller, reset sequence, or complete peripheral state machine is supplied by a list of register responses. Use that list to isolate a computation or decision. Keep captured RAM separate from MMIO and tie both to the same build/address assumptions.

13. Recovery as a chain of evidence

A recovered string is most useful when you can reproduce every step from original artifact to consumer. Preserve source range, representation, transform, parameters, output hash, and code evidence. A collection of plaintext screenshots loses the hard part.

Case file: one known XOR layer

  1. Open xor-message.bin and inspect all five bytes in Hex.
  2. In Recovery, select original offset 0, length 5, Repeating XOR, key 5a.
  3. Decode and record the output bytes 68 65 6c 6c 6f, its length, and hash.
  4. Write the byte relation for the first position: 0x32 XOR 0x5a = 0x68.
  5. Repeat the decode with a deliberately wrong key and compare the whole result. Treat this as a negative control, not a search for a lucky word.

For a repeating multi-byte key, key index depends on where the selected input begins. If code begins decoding at byte N but your range begins at N+1, the key phase may be wrong. An apparently correct algorithm can still fail because of range and phase.

Stack writes and memory captures

Static stack-string recovery recognizes certain constant-write sequences; inspect each contributing instruction and write width. Little-endian immediate stores can make the constant's printed number look reversed relative to text. Overlapping writes or intervening unsupported transformations can break a simple reconstruction.

An emulated capture has different evidence: supplied entry state, completed/partial operations, capture address, timing, and model assumptions. Compare capture length with the routine's produced length. Zero padding or stale buffer tails can create misleading strings if you capture much more than was written.

Cryptographic parameters are not decoration

SPECTRA's AES-CBC path expects an actual key, a 16-byte IV, and the admitted padded layout. AES-GCM expects a key, a 12-byte nonce, optional AAD, and ciphertext with a trailing 16-byte tag. Authentication failures can reflect wrong bytes, wrong layout, wrong AAD, or wrong key. They are not instructions to discard verification. Browser cryptographic APIs document parameter/error behavior in SubtleCrypto.decrypt; this lab exposes its own narrower controls.

Distinguish key material from a password or encoded string. A program may derive a key before use; copying its visible password text into the key box does not reproduce that derivation. Likewise, RC4 variants that discard an initial keystream prefix do not match a transform beginning at position zero.

Compression and nested layers

Verify gzip versus zlib versus raw DEFLATE framing. A decompressed result might be a configuration record, executable, or another compressed member. Use as next layer only when the resulting header/code supports that choice. Expansion is bounded to prevent one small input from consuming arbitrary memory.

For each layer, keep its own coordinate system. The record “layer 2 offset 0x20” needs a link back to layer 1 and the original source range. A transformed byte may have no single meaningful original offset. If you open it as a child investigation, preserve the parent/layer hash and chain in Notebook.

Consumer verification

The final question is “who uses the recovered data?” Follow the output pointer, length, or returned object into its next call. A string resembling a hostname may be diagnostic text; a decoded key may be unused test data. A coherent decode plus a meaningful consumer is stronger than either alone.

Deliverable: a transform ledger with input/output hashes, exact ranges, parameter sources, consumer, and unresolved steps. Exported recovery reports omit manually supplied keys, so preserve required reproduction information intentionally and privately.

16. Firmware and patch review as connected investigations

A firmware update can change an outer archive, one library, a configuration default, and a parser at the same time. Compare at the right layer. A different compressed package hash tells you the download changed; it does not identify the behavioral change.

Extract with provenance

  1. Save the old and new parent investigations with both hashes and vendor/source context.
  2. Inspect each supported container at a justified offset and export inventories.
  3. Match candidate members by path, hash, size, and identity. A matching path alone can hide a completely different component.
  4. Open relevant regular members as child investigations, keeping parent hashes and extraction metadata.
  5. Compare the two child binaries in Binary diff. Preserve unmatched and ambiguous groups.

Practice with the supplied PE pair

Now imagine a real change from a copy operation to a guarded copy. Inlining, optimization, symbol stripping, register allocation, and layout changes can destroy a simple one-to-one match. A shape match can align routines with different purposes. Stage 03 · Resolve the missing edge

The question. The dispatcher eventually uses CALL R11 instead of a literal destination. Resolve that function pointer for the supplied record. Submit the target VA as four lowercase hex digits. Distinguish the table slot's address from the function address stored inside it.

  1. Decode sub_6090. Read its BYTE field from the record, apply AND and SHR in order, and write down the returned index. The mask selects only two bits.

Read what happened

Read what happened

Read the map before the assembly. RCX and RDX are pointers, R8D is a count, and R9B holds an eight-bit key. EAX starts at zero and indexes both source and destination. R10B is temporary storage for one byte.

Stage 02 / Recover a handler

The question. Find the native handler for virtual opcode 0x13. The dispatcher uses signed 32-bit offsets relative to its table, not absolute pointers. Submit the handler VA as eight hex digits.

Why this matters. An indirect jump hides a control-flow edge until its target computation is reconstructed. Relative tables are common because they can move with their containing image. Treating a signed displacement as an unsigned absolute pointer produces a convincing but impossible target.

Read what happened

Decode file offset 0x000, length 0x61 (97 decimal), base VA 0xc000, x86-64, Little endian. Select All decoded instructions. The dispatcher reads a byte, subtracts the lowest supported opcode and checks the result before indexing the table. This establishes both the index and the table’s eight-entry bound.

Stage 03 / Build the virtual edges

The question. The virtual branch at PC 0x07 has operand 0xf7. Find its fall-through PC and taken destination. Submit those virtual PCs in that order, each as four hex digits.

Why this matters. Correct instruction boundaries are the foundation of a control-flow graph. A branch can be numerically inside a file but still point into an operand. Recovering both successors also stops one observed path from masquerading as the whole program.

Read what happened

Begin at virtual PC zero and advance by each virtual instruction’s width. Most instructions here are two bytes; DEC and HALT are one. The value 0x13 occurs both as an opcode and as an operand in this program. Its role depends on the decoding boundary, not its appearance.

The dispatcher consumes the opcode before entering a handler. Handler 15 then sign-extends the operand byte, consumes that operand and tests the saved virtual condition. Therefore the relative base is the PC after the entire two-byte instruction.

Convert 0xf7 to signed8: its high bit is set, so subtract 256 from its unsigned value. Add that signed displacement to the fall-through PC. Do not add it to the branch opcode’s location or to the native handler VA.

Why this matters. A familiar instruction can still be misread when its operand width changes. Repeated transformations magnify a small mistake: forgetting a carry wrap or resetting state can make every later branch seem inexplicable.

  1. Make a trace with PC, A, N and saved Z. Follow XOR, ADD, ROL, DEC and JNZ in the declared bytecode window.
  2. Use 8-bit arithmetic: wrap ADD at 256 and rotate eight bits, not 32. Carry the new accumulator into the next round; do not reset it to the input.
  3. Compare your first round with OBSERVATIONS.json, then complete the remaining rounds. The local Trace worksheet can check your work after you predict it.

Read what happened

The initial accumulator is the caller’s byte 0x42. The counter comes from the PPC8 header. The loop XORs A with the operand at PC 1, adds the operand at PC 3, rotates by the operand at PC 5, decrements N and tests the saved zero condition. Write the transformation as a function of the previous A.

For ADD8 keep only the low eight bits: (A + operand) & 0xff. ROL8 by one shifts bit 7 into bit 0 as well as shifting the other bits left. This is not a shift that discards the high bit, and not a 32-bit rotation. Inspect R11B in the native handlers to confirm width.

OBSERVATIONS.json is labeled BEFORE the next virtual instruction and uses decimal numeric fields. Convert carefully before comparing with your hexadecimal worksheet. It includes the first loop re-entry, not the final answer. A trace row at PC 0 after five steps describes the state entering round two.

Continue until DEC makes N zero and JNZ falls through to PC 9. Record the state before CMP changes Z. A final HALT result is not what this question asks for. Use the local worksheet only after predicting the state; compare the first differing row if your prediction fails.

Hints, one at a time

  1. Each round is ROL8((A XOR 0x23) + 0x13, 1), with the addition reduced to a byte. The counter starts at 3.
  2. Your first-round accumulator should be 0xe8. Feed it into the same transformation again; do not use 0x42 again.
  3. The second-round accumulator is 0xbd. Apply one more XOR, wrapped ADD and ROL; N is zero at the first visit to PC 9.

Response format: SPECTRA{state_aa_nn}

Enter only the full SPECTRA{...} flag. Use lowercase hex without 0x prefixes; nothing after the closing brace.

Check your reasoning: Counter decreases once per complete round. The input accumulator is not reloaded on a back edge. Record exactly where in the execution the requested state is sampled.

If your result differs: If the first round matches but later rounds differ, check state carry-over and rotations with bit 7 set. If you find A=0 at the end, you have read the later rejection result instead of the state at PC 9.

Beyond this case: Small state tables make decoder loops and interpreters auditable. Preserve width, sampling point and recurrence before replacing a loop with a high-level formula.

Stage 05 / Separate the two zero flags

The question. On the same input, examine the LAST DEC and the JNZ at PC 0x07. Submit saved virtual Z and the next virtual PC. A is nonzero here, but that alone does not decide this branch.

Why this matters. An interpreter has guest state as well as the host CPU state used to implement it. Confusing those layers can reverse your interpretation of a branch even when every disassembled instruction is correct.

Open these files: interpreter.bin, puppet-core.ppc.

  1. Decode handler 14 and find where SETE stores the condition. Decode handler 15 and find which stored value its TEST reads.
  2. Track the final counter decrement. Ignore unrelated native flags changed by the dispatcher between virtual instructions.
  3. Write why nonzero A does not force this JNZ to loop. Submit saved Z as two hex digits and next PC as four.

Read what happened

Handler 14 decrements R12B and immediately executes SETE R13B. This turns the native zero flag from that decrement into an explicit stored byte, 0 or 1. R13B is now the guest condition. Later native arithmetic can change CPU flags without changing this stored byte.

Follow the dispatch path to handler 15. It consumes the branch operand and then TESTs R13B. The native JNZ goes back to dispatch when saved Z is nonzero, which implements the virtual JNZ NOT taking its relative edge. Read the effect, not merely the shared mnemonic.

After the final decrement the counter is zero, so saved Z is true. The virtual branch falls through. The accumulator is not the tested value. This is a useful point to distinguish a guest instruction called JNZ from the multiple native instructions implementing it.

As a local follow-up, trace the bytes 16 42 12 01 15 02 10 01 17 on paper with input 0x42. CMP saves true, ADD changes A but leaves saved Z alone, and the virtual branch follows that saved value. Predict before tracing; this optional example is not another flag.

Hints, one at a time

  1. DEC writes the counter, then SETE stores whether that counter became zero into R13B.
  2. At the final iteration N becomes zero. R13B becomes 1 even though the accumulator remains nonzero.
  3. Virtual JNZ takes its displacement only when saved Z=0. With Z=1 it continues immediately after the two-byte branch.

Response format: SPECTRA{branch_zz_pppp}

Enter only the full SPECTRA{...} flag. Use lowercase hex without 0x prefixes; nothing after the closing brace.

Check your reasoning: Point to the writer of saved Z and the later reader. A statement such as “JNZ means A is nonzero” is incomplete unless you have proved what set its condition.

If your result differs: Native condition flags are implicit; virtual Z here is explicit in R13B. Do not substitute a debugger’s current CPU ZF at the dispatcher for the stored guest condition.

Beyond this case: When lifting interpreted code, model guest registers and condition state explicitly. Host instructions are the implementation, not the guest semantics.

Stage 06 / Invert the acceptance path

The question. Recover the one input byte that makes the ORIGINAL bytecode halt with result 1. Derive it from the comparison and inverse loop, then validate it forward. Do not patch the program.

Why this matters. Being able to translate a trace into a reversible expression is a practical step beyond reading instructions one at a time. It lets you recover a condition analytically and then test the explanation rather than guessing at a flag.

Open these files: puppet-core.ppc, FORMAT-NOTES.txt.

  1. Find the CMP operand and the two result-setting paths in puppet-core.ppc. Explain which path represents acceptance.
  2. Undo one loop round in reverse order: ROR8, subtract modulo 256, then XOR. Repeat for the header’s number of rounds.
  3. Trace your candidate forward, including CMP, virtual JNZ and HALT. Check status=0 separately from result=1. Submit the original input byte.

Read what happened

Start at the end: the program compares transformed A against an immediate. When equality holds, saved Z is true, the following JNZ falls through, LOAD sets A to 1 and HALT returns it. The alternate branch loads 0. Verify these paths in your virtual control-flow graph.

The target is the value BEFORE CMP, not the later result 1. One round applies XOR, ADD and ROL in that order. To invert a composition, reverse both the order and the operations: rotate right, subtract the addition operand modulo 256, then XOR with the same XOR operand.

Apply that inverse once per round. Keep each intermediate value as a byte and annotate which round you are undoing. A wrap in subtraction is expected. ROR8 is a circular rotation, not a right shift and not a rotation of a whole machine word.

Run the candidate through your forward ledger or the local worksheet. You should reach the comparison target after the last round and a valid HALT with result 1. Change the input by one and observe another path. An optional exhaustive check covers 256 inputs, but do not replace the explanation with a brute-force result.

Hints, one at a time

  1. The target comparison value is 0xa7. The forward round is XOR 0x23, ADD 0x13 modulo 256, then ROL8 by 1.
  2. Undo a round as (ROR8(value,1) - 0x13) modulo 256, then XOR 0x23. Do this three times.
  3. The first inverse round produces 0xe3, and the second produces 0xfd. Apply the same inverse once more, then validate that candidate through all three forward rounds.

Response format: SPECTRA{input_xx}

Enter only the full SPECTRA{...} flag. Use lowercase hex without 0x prefixes; nothing after the closing brace.

Check your reasoning: Prove the candidate both backwards and forwards. Distinguish input, transformed comparison value and final result. Only the input belongs inside this flag.

If your result differs: If you obtained the comparison immediate itself, you skipped the inverse rounds. If you obtained 01, you found the result. If a negative subtraction remains negative, reduce it modulo 256.

Beyond this case: Inverse operations help recover checks, encodings and simple key schedules. They apply only when the modeled operation is reversible; a lossy mask or hash requires different reasoning.

Stage 07 / Diff the interpreted behavior

The question. The variant changes one byte. Find its absolute container offset and the VARIANT’s accepted input. Submit the four-digit file offset and two-digit input; explain whether the change is an opcode or an operand.

Why this matters. A tiny data patch can change program behavior without changing a single native instruction. A byte diff tells you where evidence differs; its semantic effect comes from the interpreter and instruction boundaries you already recovered.

Read what happened

The Raw byte comparison table works without matched functions. Keep ORIGINAL as the main file and VARIANT as the comparison so before/after direction is clear. Expect one modified byte and no size change. Do not infer that an empty function table means the files are identical.

Subtract the bytecode start from the modified container offset. Find the virtual instruction whose byte span includes that PC. It is an operand to the preceding instruction. Stage 08 / Keep failure separate

24. Build a research package someone else can use

A good handoff lets another analyst continue without adopting your assumptions blindly. Preserve the smallest artifact set that reproduces the claim and enough context to distinguish observation from supplied state.

The package

  • Case summary: question, conclusion, evidence locations, uncertainty, and next test.
  • Identity manifest: original/child/dependency hashes, origins, format, CPU, and mapping.
  • Analysis record: engine/app version, budgets, unresolved targets, signatures/types, hypotheses, and relevant exports.
  • Experiment recipe: entry, ABI, input bytes, buffers, virtual files, hooks, MMIO, and intended stop.
  • Observed evidence: completed/partial stop status, returned values, output/layer hashes, event/coverage bounds, and checkpoints where useful.
  • Sharing decision: whether samples, private data, and keys are included. A public report need not include the entire project.

Imported traces are evidence, not truth by import

A supplied trace may be useful without being replayable. Record its origin, engine/version, ordering, mapping, completeness and modifications. SPECTRA now imports bounded observation formats and records persistent segments. Routine history reconstructs supported x86/x64 bare-routine states; arbitrary imported observations do not become verified replay or full-process time travel.

For experiments, select the appropriate artifact: the compact trace retains the latest 200 attempts; a persistent recording retains ordered observations within its explicit budget; a checkpoint represents supported state reconstruction. Explain capture boundaries and completion. None can establish an omitted beginning of a run.

Final case assignment

Choose one path: ARM PIE relocation, Windows clock hook, Linux byte-preserving echo, ARM MMIO, a native diff, or managed method selection. Produce two controlled cases that separate two explanations. One case should challenge your preferred explanation, not merely repeat it with another pleasant input.

Examples: vary a field believed to control a branch; supply EOF instead of normal input; change a clock hook that you believe is irrelevant; relocate a static PIE and update every address; or inspect whether a managed label survives reading the actual method references.

Review yourself

  1. Could someone identify the exact artifact without the filename?
  2. Could they distinguish all address spaces and transform layers?
  3. Are supplied values clearly separate from recovered values?
  4. Does the stop status support your claimed result?
  5. Did you preserve uncertainty in matches, boundaries, types, and missing environment behavior?
  6. Would the conclusion still be true if a label or generated name were removed?
  7. Can another reader reproduce the small claim with the retained assets?

That is the skill this manual is building: making SPECTRA answer a precise question and leaving enough evidence for the next person. Bigger engines and more profiles can expand the questions. They do not replace this discipline.

Prepare an exact selective bundle

Use Notebook's nine-group evidence selector with findings-only defaults. Inspect the prepared member inventory, per-member sizes and SHA-256 before downloading. Original, recovered, dependency and comparison bytes each have independent inclusion controls. Notes, recipes and traces can themselves contain secrets; selection is not redaction.

Validate an offline handoff by opening the completed artifact in a clean investigation and confirming identities and selected evidence.

SPECTRA // GHOST CIRCUIT

004/01 · The argument trail
SPECTRA{edx_0007}

At 0x600b, MOV EDX,7 supplies argument two for CALL 0x6080. RCX contains the record address 0x6140. In this Windows x64 fixture, integer results use EAX. LEA supplies an address, not the record contents.

004/02 · Recover the record
SPECTRA{field_012c}

MOVZX EAX,WORD [RCX+2] reads file bytes 2c 01 at 0x142: unsigned 0x012c (300). The later ADD EAX,EDX adds 7, so the first helper returns 307 = 0x0133. The flag requested the field before that addition.

004/03 · Resolve the missing edge
SPECTRA{target_60c0}

record[1] is 0x2a. (0x2a & 0x0c) >> 2 = 2. Slot VA is 0x6160 + 2*8 = 0x6170, file offset 0x170. Its bytes c0 60 00 00 00 00 00 00 hold VA 0x60c0. CALL R11 therefore selects that routine. The mask bounds all byte inputs to four table entries.

004/04 · Keep the width
SPECTRA{byte_03}

The byte at record+4 is 0xd6. ROR8 by 3 gives 0xda; 0xda + 0x29 = 0x103. ADD AL keeps 0x03, discarding the carry beyond eight bits. MOVZX EAX,AL makes the final EAX exactly 3. A 32-bit rotation would be a different transform.

004/05 · Across the calls
SPECTRA{result_0136}

The first call returns 0x0133 and stores it at caller RSP+0x20. EAX is then reused for index 2 and for selected transform result 3. The final ADD restores the saved contribution: 0x0133 + 3 = 0x0136 (310). The index is not added. Calls may clobber volatile registers, so use the actual saved value.

004/06 · Draw the machine
SPECTRA{states_100123}

Starting from zero, AXBABC yields states 1,0,0,1,2,3. X consumes a byte and resets; B cannot advance state zero. State 3 is absorbing: every following byte leaves it at 3. States above 3 return zero. This state routine is separate from the dispatcher.

004/07 · Break your hypothesis
SPECTRA{b_0_3}

Model B exactly matches the routine. On AABC the real states are 1,0,0,0, ending 0; model A gives 1,1,2,3, ending 3. From state 3, X leaves the real routine and B at 3, while model C returns 0. These counterexamples distinguish reset, restart and terminal behavior.

SPECTRA // HOLLOW SIGNAL

005/01 · Bound the evidence
SPECTRA{range_0020_001f}

Header +6 contains 1f 00: 31 bytes. Header +8 contains 20 00 00 00: file offset 0x20. The half-open range is [0x20,0x3f), so the last byte is 0x3e. Decoded output starts at its own offset 0. Tail text is outside the declared configuration.

005/02 · Recover the moving key
SPECTRA{key_8c}

The first byte uses key 0xa7. Only AFTER that XOR does ROL R9B,1 rotate 10100111 to 01001111 (0x4f); ADD R9B,0x3d gives 0x8c. Thus the second byte uses 0x8c. Updating first or rotating 32 bits produces a different transform.
