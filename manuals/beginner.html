1. You belong at this workbench

You do not need an expensive license, a shelf of computers, or a job title to start reverse engineering. You need a question, something to inspect, and a way to keep track of what you learn. This book gives you all three. We will begin with tiny harmless programs and work toward a defensible investigation of an unfamiliar file.

Reverse engineering (RE) means working backward from an artifact to understand its design and behavior. Our artifacts are mostly compiled programs: files whose original source code may be missing. We inspect bytes, recover instructions, follow relationships, reconstruct useful explanations, and test small hypotheses. The goal is understanding you can show someone else how to reproduce.

That can mean figuring out how malware stores its configuration. It can also mean understanding an old file format, checking a vendor's patch, documenting a device's firmware, or finding which part of your own desktop client builds a request. A suspicious file is one use case. Curiosity is a much bigger one.

How this book works

Read chapters 1-6 in order. They explain the vocabulary used everywhere else. Then complete the Windows, Linux, and ARM investigations. Later chapters introduce controlled execution, managed code, decoding, firmware, and comparisons. Each case has a specific question, steps, expected observations, a notebook entry, and a checkpoint. Answers are included so you can learn without waiting for someone to grade you.

Bold text names a SPECTRA control. Monospaced text is an exact value, filename, instruction, or example. Addresses beginning with 0x are hexadecimal. A value labeled example is teaching data, not a claim about an unknown malware sample. Save your current investigation before loading any demo: demos replace the active file.

Your setup

  1. Open SPECTRA in a current browser. The book describes release 0.18, checked against its source and fixtures in November 2026. Future labels or limits may change.
  2. Keep this manual beside it, or switch between tabs. On a phone, use the menu to select a section and scroll to the relevant controls. A wider view helps with assembly, but a keyboard is not required for the early lessons.
  3. Go to Training ground. Keep Explanations on while learning. Use the built-in exercise buttons when a chapter names one.
  4. Save useful work in Notebook and download a project before a long break. Mobile browsers can discard background tabs; browser storage is convenient, not a permanent backup.

The companion practice folder contains benign files for the additional lessons. You can use the built-in demos without downloading it. The book's HTML and PDF can be read offline; first use of SPECTRA's analysis engines needs their assets, unless you already have the complete offline release. Downloading one HTML page is not the same as downloading all engines.

A realistic promise

SPECTRA brings useful static analysis and bounded emulation into the browser. It is not every operating system or device in a tab. A supported CPU does not imply every instruction, executable, library, or system call will work. Learning to recognize the boundary is part of learning RE. When something stops, we will ask what assumption failed instead of treating the stop as your failure.

First checkpoint: Write one question in Notebook before opening a real sample. Good: “Which bytes become the configuration path?” Too broad: “Tell me everything about this malware.” A small question gives your investigation a finish line.

Choose your route

This edition follows SPECTRA 0.18 and the eight public CTF campaigns available on 11 November 2026. Start with the foundations and Windows/Linux/ARM cases, then try the Android package and the first three CTF campaigns. You can read a single case at a time; there is no prize for rushing past an unfamiliar word. Keep a small note of the next question before you close the tab.

Teaching is optional in SPECTRA. It defaults off; use the explanations button at the top to turn it on. The examples here explain the same evidence in more depth. Read these books alongside the workbench, or download the PDFs and practice files to keep learning offline.

2. What RE actually does

Imagine finding a small device with no manual. You can inspect its parts, follow its wires, and carefully test a button. Software gives us similar choices. Static analysis studies the file without running its instructions. Dynamic analysis observes an execution. SPECTRA's debugger executes supported instructions inside a model, which is a particular kind of experiment rather than a complete real computer.

Four views of the same thing

  • Bytes: the stored data. Hex explorer shows these directly. They are the anchor when an interpretation gets confusing.
  • Assembly: bytes decoded as instructions for a selected CPU. Disassembly answers what those instructions express, given the selected mode and mapping.
  • Reconstructed code: a decompiler's higher-level explanation. It can expose conditions and loops, but names, types, and structure may be inferred.
  • Observed state: registers, memory, output, and traces from one controlled run. These show what happened under the inputs and environment you supplied.

These views should support each other. Suppose reconstructed C says a loop XORs bytes with 0x5a. Assembly should contain the corresponding operations. A memory capture after the loop should show the predicted output. If they disagree, you have a useful question: wrong range, wrong type, wrong entry, wrong input, or an incomplete engine model?

Malware, without the movie version

Malware is software used to cause unauthorized harm: stealing information, disrupting systems, taking control, or enabling those actions. A loader may prepare another program. A downloader may fetch a payload. A backdoor may accept commands. A stealer may collect sensitive data. These roles can overlap, and a family label does not describe every file with that label.

Ordinary software also reads files, uses cryptography, talks to servers, and changes settings. Seeing WriteFile, a URL, or an encryption library is not enough to call a program malicious. Ask who initiates the behavior, what data it handles, which conditions lead there, and what authorization/context exists. RE supplies technical evidence; it does not turn one interesting string into intent.

The investigation loop

  1. Observe: “This file contains the text /api/status at this offset.”
  2. Hypothesize: “A routine may use it to construct an HTTP request.”
  3. Test: follow references, inspect argument setup, identify the caller, and check whether that route reaches a networking operation.
  4. Revise: perhaps it is a test fixture, documentation, or an unused error message.
  5. Record: save the original evidence, your interpretation, and what remains untested.

A finding is stronger when another person can retrace it. “I found C2” is weak without context. “The routine at this VA copies this decoded hostname into this request object; actual network contact was not tested” is precise. C2 means command-and-control, but don't give a hostname that label until you have a reason.

Your first analyst habit

Keep three headings in every case: Observed, Likely explanation, and Still unknown. This is not academic fuss. It keeps your own guesses from becoming facts when you return tomorrow.

Checkpoint: You find the word “password.” What have you proven? Answer: Only that those bytes were extracted as text. You have not proved password theft, a valid credential, or even that the program uses the string. The next useful step is its code or data context.

3. Bytes, hex, text, and numbers

A file is a sequence of bytes. One byte contains eight bits; each bit is zero or one. A byte can represent a value from 0 through 255. We usually write bytes in hexadecimal because two hex digits describe one byte neatly. Hex digits run 0-9, then A-F for ten through fifteen.

0x10 means sixteen, not ten. 0xff means 255. 0x100 means 256. The prefix tells you the number base; it is not part of the stored bytes. A range with offset 0x20 and length 0x10 begins at byte 32 and contains 16 bytes, ending at offset 0x2f. The next byte is 0x30.

Read a hex row

offset   bytes                   possible text
0x0000   68 65 6c 6c 6f 00        hello.

The left column is a location, the middle is data, and the right is a convenient text interpretation. Here the five readable bytes spell hello. The zero byte may terminate a C-style string. A dot in a hex viewer usually means “not displayed as a printable character.” It does not always mean the underlying byte is zero.

One set of bytes, several interpretations

41 can be decimal 65, the ASCII character A, part of an instruction, or one byte of a larger value. Context decides. A four-byte integer stored as 78 56 34 12 has value 0x12345678 in little-endian order. In big-endian order those same bytes have value 0x78563412. Endianness is the order of bytes inside a multi-byte value; it does not mean that a word is read backward letter by letter.

Unsigned numbers use all bits for nonnegative values. Signed two's-complement numbers interpret the top bit as part of a negative representation. The byte ff can mean unsigned 255 or signed -1. The instruction and declared type determine which interpretation matters. This is why a guessed signed comparison in decompiled code deserves a look at assembly.

Text is an encoding choice

ASCII covers a small character set. UTF-8 uses one or more bytes per character. UTF-16 uses two-byte code units and sometimes pairs of them. Plain English “Hi” can appear as 48 69 or, in UTF-16 little endian, 48 00 69 00. Searching only one representation can miss the other. SPECTRA's wide-string extraction focuses on ASCII-range characters in UTF-16 patterns, so it is not a complete multilingual text decoder.

Encoding changes representation, such as Base64. Compression reduces redundancy, such as gzip. Encryption protects data using a key and an algorithm. All can make plain text disappear from the file. A successful Base64 decode does not mean you broke encryption.

Hashes and identity

A SHA-256 hash is a compact fingerprint computed from bytes. Renaming a file leaves its hash alone; changing its bytes normally changes the hash. Use it to identify exactly what you inspected. A hash is not a verdict, an author identity, or a guarantee of safety. When a download page and SPECTRA show different hashes, first check whether one describes the archive and the other describes the extracted member.

Mini-lab

  1. Open Decoder lab. Choose Hex → UTF-8 text.
  2. Enter 68 65 6c 6c 6f and choose Run transform. Expect hello.
  3. Choose Base64, enter aGVsbG8=, and run. Expect the same output.
  4. Write down why the inputs differ even though their decoded text agrees.

Answer: They encode the same five bytes in different printable representations. Preserve the original representation and transform if you use this in an investigation. A copied output alone loses how you got there.

4. A tiny computer inside your head

You do not need to memorize a CPU manual. Start with a handful of ideas. A CPU fetches an instruction, operates on values, and chooses the next instruction. A register is a small named storage location inside that CPU. Memory is a larger addressed space. The program counter identifies the next instruction; stack and general registers support the work around it.

Instructions you will keep meeting

JobWhat to look forUseful question
Move, load, storeCopy a value or access memoryIs this a pointer, its contents, or a plain number?
Add, subtract, shift, XORTransform valuesWhich input contributes to this result?
Compare and conditional branchChoose a pathWhich condition takes the other path?
Call and returnEnter a routine and come backWhat arguments went in, and what came out?

A pointer is a value used as an address. If R0 contains 0x2000, reading R0 gives you 0x2000. Reading memory at that address gives you the bytes stored there. Confusing the two causes many beginner debugger faults. If a routine expects a pointer to a string, giving it the number 3 is not giving it a three-character string.

Functions and the stack

A function is a reusable piece of work. It can accept arguments, use temporary values, call other functions, and return a result. The stack is memory commonly used for call bookkeeping and temporary storage. A heap is memory used for allocations with more flexible lifetimes. Global data lives in another part of the program's mapped memory.

A calling convention, part of an ABI, says where arguments and results belong. For our ARM addition lesson, inputs use R0 and R1 and the result uses R0. For an ordinary Windows x64 integer call, the first four argument positions use RCX, RDX, R8, and R9; a simple scalar result uses RAX. The caller also reserves stack space. This is why selecting the right ABI matters even when the CPU setting is correct. Microsoft's x64 calling convention and Arm's AAPCS32 describe the formal rules; the labs teach a small integer subset.

CPU is not operating system

Windows and Linux are operating systems. ARM, AArch64, x86, and x86-64 identify CPU instruction families/modes. A Windows ARM64 executable and a Linux ARM64 executable can target related instructions while expecting different loaders and APIs. A filename ending in .exe does not mean x86. An ELF file does not mean ARM. Read the header.

Thumb is an ARM instruction mode, not a different operating system. AArch64 is the 64-bit Arm instruction set. RISC-V and MIPS are other families. The same raw bytes decoded in the wrong mode can produce plausible-looking nonsense. You need evidence for CPU, byte order, address mapping, and environment before execution.

Loops and branches

A loop repeats instructions while a condition holds. A basic block is a run of instructions with no internal branch entry/exit except its boundaries. A control-flow graph connects blocks with possible paths. An arrow tells you a possible connection, not how often it runs. A debugger trace, by contrast, records a path actually taken under one setup.

Checkpoint: A file is ARM64 PE. Can you select Linux ARM64 and expect it to run? Answer: No. The CPU may match, but the executable loader, calling environment, dependencies, and API expectations do not. Static disassembly/decompilation can still be useful.

5. What is inside an executable?

Most executable files contain instructions plus a map describing how to load them. Headers identify the format and CPU. Regions separate code, read-only constants, writable data, metadata, and other content. A file can contain much more than the bytes its CPU will execute.

PE, ELF, managed assemblies, and raw files

PE is the Windows executable image format. Its machine field distinguishes CPU targets, and its section table describes regions. An RVA is a virtual address relative to the image base; a file offset is a position in the stored file. They are usually different. The Microsoft PE specification defines those terms and fields.

ELF is used by Linux and other systems. Its header carries class, byte order, machine, and entry information. Program headers describe what the loader needs; section headers organize content for other purposes. The ELF header specification is a useful reference when checking a field. SPECTRA's actual loader support is narrower than the entire ELF format.

A .NET assembly commonly uses a PE container but contains managed metadata and intermediate language (IL). Use ILSpy to reconstruct C# from suitable managed content. Ghidra handles supported native machine code. Some files mix managed and native pieces; do not assume one engine explains everything.

Raw firmware or raw code may have no useful executable header. You must supply the range, CPU, byte order, and load address. A raw-mode button is not a detector. It applies your assumptions to bytes.

Imports, exports, symbols, and entry

An import describes a dependency requested from elsewhere, such as a library function. An export exposes something for other code to use. A symbol gives an address a name or other metadata. Symbols may be removed from a release build. A stripped binary can still contain code; it simply gives you fewer labels.

The entry point is where a loader transfers control, not necessarily the program's main logic. Startup code can prepare runtime state first. Static linking includes library code inside the file; dynamic linking expects dependencies to be supplied later. “Zero imports” can mean a static binary, incomplete parsing, or a different mechanism. It is not a promise that execution needs no environment.

File bytes versus loaded memory

Suppose a section begins at file offset 0x200 and is loaded at VA 0x140001000. A byte 0x20 bytes into that section is at file offset 0x220 and VA 0x140001020. The relationship applies only inside that mapped, file-backed range. Zero-filled BSS can exist in memory without corresponding file bytes. Do not add an image base to every file offset.

Relocations are records used to adjust address-dependent data when an image loads somewhere else. Position-independent code can accommodate movement in other ways, but a position-independent executable may still need relocations. The intermediate manual watches a benign ARM example in detail. For now, record which address space you mean every time you write a location.

Mini-lab: make an identity card

  1. Load a built-in demo and open File structure.
  2. Record filename, SHA-256, format, CPU, byte order, entry, and region names.
  3. Locate a code region and note its file offset and VA separately.
  4. Open that file offset in Hex explorer. Confirm you are viewing the same region.

Checkpoint: Why can a memory address have no file offset? Answer: The loader or program can create zero-filled or allocated memory. A runtime stack, heap buffer, or BSS region need not have stored bytes at an equivalent disk location.

Start with the top-level Load demo. This loads Northstar, a synthetic teaching PE. It contains clues chosen for practice; it is not evidence of a real intrusion. If you already have work open, save it first. Our question is simple: “What can I say about this file without executing it?”

The top of the workspace

The file card identifies the active bytes and hash. The summary tiles count extracted strings and heuristic indicator strings, show entropy, and summarize structure. Entropy measures how varied byte values are in a region. Compressed data, encrypted data, and ordinary media can all have high entropy. A low-entropy region can still matter. Treat the byte landscape as a place-finding aid, not a danger meter.

“Analysis complete” at the file level means the basic pass finished. It does not mean every function has been recovered, every engine ran, or every behavior is known. Each engine has its own status. Read those statuses when you change sections.

7. One byte, three addresses: learn the map

You found a string at file offset 0x440. A code view shows 0x140002040. Someone else calls it RVA 0x2040. Nobody has to be wrong: these can be three coordinates for the same bytes. Before following references, name the coordinate system. An address without a coordinate system is like a street number without a street.

File offset: where it lives on disk

A file offset counts from the first byte of the file, which is offset zero. Hex explorer reads those stored bytes. Offset 0x440 means 1,088 bytes from that beginning. It does not imply the computer places the file at memory address 0x440. Headers, alignment and loading rules intervene.

VA and RVA: where the program expects it

A virtual address, or VA, names a location in a process's address space. A PE relative virtual address, or RVA, measures from that image's base. For an image base of 0x140000000, RVA 0x2040 gives VA 0x140002040. The base is an assumption about this image, not a universal Windows constant. A loader can move an image; a runtime map can differ from the preferred header map.

Suppose a PE section begins at file offset 0x400 and RVA 0x2000. The byte 0x40 bytes into that section has file offset 0x440 and RVA 0x2040. The general rule within this section's file-backed span is RVA = section RVA + file offset - section raw offset. Do not apply it to an offset outside the section just because the subtraction produces a number.

Walk it in SPECTRA

  1. Open a PE and choose File structure. Find Address mapping ledger.
  2. Choose Declared file headers as Mapping source. Set Input space to File offset, enter a known offset from Strings, and choose Resolve address.
  3. Read the region name, candidate address and classification. If an original file byte exists, Inspect original bytes takes you to it. Verify the same text or bytes.
  4. Resolve the reported VA in the other direction. A successful round trip within the same mapping is a consistency check, not independent proof that the program will load there.
  5. Choose Export mapping ledger and keep it with your note. Write which mapping source you used.

When there is no matching file byte

Programs often reserve memory that starts as zeroes. ELF BSS is a familiar example: a load segment's memory size can exceed its stored file size. A byte in that extra range is real mapped memory, but it has no stored source byte at some later file offset. The correct answer is zero-fill, not a guessed offset. Memory allocated during an experiment can likewise have no file origin.

Conversely, an overlay can be stored at the end of a file without being part of its ordinary loaded image. File-only is useful information. An address can also be unmapped, or match overlapping declared regions. Keep ambiguity visible until other evidence resolves it. Do not pick the first row merely to get a clickable answer.

Raw code and extracted children

For a small raw range, select Current raw disassembly range. Its base VA applies to the first byte of the selected range, not automatically the beginning of the whole file. In a range starting at file offset 0x80 and VA 0x6080, a byte at file offset 0x83 maps to VA 0x6083. The flat-image CTF maps explicitly supply these relationships.

After extracting a compressed child, its offset zero belongs to the child. It does not become a simple parent offset by adding the archive header size. Preserve parent hash, member path, extraction description and child hash. Those facts reconnect your investigation without inventing a linear relationship through compression.

Practice and explain

Write three columns in Notebook: file offset, VA and mapping evidence. Fill one row for a known string and one for a zero-filled region, if the file has one. For the second row, use “no stored file byte” where appropriate. The skill is explaining when a conversion is valid, not forcing every cell to contain a number.

If you get stuck: confirm that the active sample is still the intended file. A child investigation or comparison can leave you looking at another artifact. Then check hexadecimal notation, section boundaries, image base and mapping source, in that order. Exact 64-bit address arithmetic in the ledger does not make every such address executable in the debugger.

8. Case file: a Windows PE from bytes to meaning

Question: How does a program announce itself and write data? Open Debugger lab, select x86-64, and choose Load Windows demo. The button loads a benign x64 PE and prepares a modeled session. For this chapter, inspect it statically before pressing Run. The companion copy is windows-model-x64.exe.

Build its identity

  1. Go to File structure. Expect PE32+, x86-64, and three named regions: .text, .data, and .bss.
  2. Record the preferred image base 0x140000000 and entry VA 0x140001000. The entry's file offset is 0x200 in this fixture.
  3. Open Hex explorer at 0x200. These are entry code bytes, not a text message.
  4. Find the imports. This fixture names OutputDebugStringA, GetTickCount, Sleep, ExitProcess, CreateFileA, and WriteFile from kernel32.dll.

Those names are clues to expected services. OutputDebugStringA suggests diagnostic output. CreateFileA and WriteFile suggest file activity. They do not tell you whether the calls are reached, what arguments they receive, or what a real system would allow.

Follow the message

  1. In Strings, search SPECTRA:. Expect SPECTRA: hello from the Windows model.
  2. Select it and use View bytes. The message begins at file offset 0x500. Its VA is 0x140002100.
  3. Choose Find code references. Open the instruction that prepares the address.
  4. In Disassembly, inspect the following indirect call through an import slot. On this x64 example, the message pointer is prepared in RCX for the first argument.
  5. Use the instruction context and import information to connect that call to OutputDebugStringA.

Notice the difference between loading an address and loading its contents. An address-calculation instruction can put a pointer in RCX without reading the string itself. The called service receives that pointer and decides what to do with the bytes.

Follow the file path

Search for spectra-demo.txt. The path is stored at file offset 0x700, mapped at VA 0x140002300. Follow its reference and compare the caller's setup with the message's setup. Later code passes a handle returned by CreateFileA to WriteFile. A handle is a value identifying an object in the environment; it is not automatically a file pointer in memory.

Give the entry a modest working name such as demo_message_and_file using Name / annotate. Include the reason in the comment. A name saves you navigation effort; the comment preserves your evidence. If your hypothesis changes, rename it.

Reconstruct, then check

Send the function to Decompile, choose the native Ghidra engine, and use the selected function. Read the output beside the assembly. Indirect calls may look less friendly than a hand-written C program. SPECTRA's current Ghidra bridge does not carry every Windows import-slot type into reconstructed C. Use Native imports · check indirect calls here and Cross-references to resolve that context.

Write this conclusion: “This benign PE contains a message and path referenced from entry code. The code prepares calls through named Windows import slots. Static evidence suggests debug output and a file write. Whether those calls complete is the next controlled experiment.”

Checkpoint

Why is “the program created a real file on my computer” unsupported here? Answer: Static inspection did not execute it. Even the following debugger lesson uses virtual files inside an explicit model. You must distinguish intended operation, modeled behavior, and actual host activity.

9. Case file: the Linux marker that does not call home

Question: Does a hostname-looking string imply a network connection? Open Training ground → Load the ELF exercise. This loads the provided spectra-first-reference.elf and searches for its marker. The companion copy is first-reference.elf.

Meet the file

The bundled artifact is ELF64, little endian, x86-64, with an entry at 0x401020. It has symbols that help us learn. The entry is startup code; the interesting logic is in main and fixture_helper. If you compile the included source yourself, addresses and metadata may differ. Use the bundled file for matching observations.

  1. In Strings, select SPECTRA_FIXTURE_ONLY.example.
  2. Record its offset and choose Find code references. Open the referring instruction.
  3. Find the surrounding function and the call to fixture_helper. Use the Functions list if the symbol makes navigation easier.
  4. Decompile main, then fixture_helper. Read how the argument travels between them.
  5. Return to Training ground and choose Check my evidence. The check looks for the decoded reference; merely finding text is not enough.

Read the source after you investigate

static const char marker[] = "SPECTRA_FIXTURE_ONLY.example";
int fixture_helper(const char *s) { return s[0]; }
int main(void) { return fixture_helper(marker); }

const char *s describes a pointer to character data that this function does not modify through that pointer. s[0] selects the first character. The marker begins with S, ASCII 83 decimal or 0x53. Main returns the helper's result. There is no network operation in these two source functions.

Look back at the assembly. You should be able to explain one concrete chain: the caller prepares a pointer, passes it to the helper, the helper reads a byte, and a return value comes back. You do not need to understand every instruction in the entire executable to answer this question.

The zero-caller and zero-import traps

Functions may appear to have no known callers when runtime startup, callbacks, or incomplete recovery supplies the connection. Likewise, a library/import count is only what the parser and file representation expose. Never substitute those counts for reading the relevant path.

This teaching ELF contains ordinary linked startup machinery. It is useful for static RE; it is not the simple syscall-only ELF used in our later process-model lesson. If Debugger preflight reports an interpreter or dependency it cannot provide, stop there and use the dedicated Linux demo. Clearing the warning by pretending the whole file is raw code would discard the very environment the program expects.

Assembly gets close to the CPU; reconstructed C or C# gets closer to how people discuss logic. SPECTRA uses a browser integration of Ghidra for native code and ILSpy for managed code. Names, types, and appearances

Generated names such as param_1, local_8, or sub_... are organizational aids. A variable reused by a compiler may appear as one thing in one view and several temporaries in another. Optimized code can inline functions, remove unused paths, combine arithmetic, or replace branches with other operations.

A type controls interpretation. char * suggests a pointer to characters. uint32_t is an unsigned 32-bit integer. A struct describes fields at offsets in a block of memory. Common confusing output

  • Indirect call: the target comes from a pointer or slot. Look at imports and cross-references rather than inventing a callee.
  • Unexpected parameters: the ABI or function boundary may be wrong, or a register may really depend on caller state.
  • Lots of casts: widths, signedness, or missing types need attention. Some casts express real behavior.
  • Unstructured jumps: optimization, unusual control flow, or missing edges can prevent a neat loop/if reconstruction.
  • Failure: check function VA, CPU, mode, byte order, mapping, and supported engine profile before assuming the bytes are protected.

12. Debugging means controlling a question

A debugger lets you pause execution, inspect state, and decide what to do next. SPECTRA's Debugger lab does this for supported emulated code and explicit process models. It does not attach to a real Windows process, boot Linux, or supply a complete device. You can still answer valuable questions if you keep the experiment small.

Before Initialize

  1. Choose Use detected setup for an executable and read the load check. For raw code, supply a justified CPU, byte order, range, load VA, and start VA.
  2. Choose the environment: Bare routine, Windows process model, or Linux ELF process model. Format and CPU support must both fit.
  3. Decide whether you are beginning at program entry or calling a function with prepared arguments. Those require different state.
  4. Check dependencies and unsupported features listed by preflight. A passing load check proves a mapping can be prepared, not that the whole run will finish.
  5. Initialize, inspect the starting memory/registers, and save a baseline checkpoint before changing anything important.

The controls, in human terms

ControlUse it whenRead the stop reason
Step instructionYou want to see one supported operation's effectSome architectures combine a branch and delay slot
Step overYou want to pass a call and return to its callerA fault or breakpoint can stop it early
Step outYou want to return from an observed call frameStarting mid-function may provide no usable call history
Run / continueYou have a breakpoint or a bounded questionA budget stop is not a normal exit
PauseYou need to stop a running batchInspect the last complete state and any deadline warning
Reset sessionYou want the last initialized setup againIt does not apply newly edited setup fields

Breakpoints and watchpoints

A breakpoint says “pause before reaching this instruction address.” Set Breakpoint VA and choose Add breakpoint. It is a VA in the loaded session, not a file offset. A conditional breakpoint also checks a supported register comparison. Use it to stop when a loop counter reaches a chosen value; it is not an arbitrary scripting expression.

A watchpoint says “pause when this memory range is read or written.” Under Watch memory, select the VA, size, and access kind. A write may already be visible when the pause appears, so inspect the preceding operation. Watching one output buffer is more useful than watching the entire address space.

Registers, memory, and evidence

Read memory uses a memory VA. Show scratch and Show stack are shortcuts to supplied working areas. Patch session bytes changes the emulated copy; Hex explorer still shows the original file. Set a register changes your experiment. Record edits so another analyst does not mistake them for naturally occurring state.

The live execution preview retains the latest 200 attempts. Persistent recording can retain more observations within its explicit budget; it must start before the execution you want to preserve. API/model events have their own bounds. Stop near the event you care about, save an experiment, and capture useful memory to Recovery. A register shown after a fault is intermediate state; call it a returned value only after a completed return.

Save and resume an experiment

Under Saved experiments, name and save a checkpoint. SPECTRA restores by replaying recorded execution and edits in a fresh emulator, then verifies the result. It needs the same sample and engine build. Importing a checkpoint is not the same action as replaying it. A verification failure means the restore did not establish the expected state.

A known transform is stronger when code supplies its parameters. For multi-byte XOR, selecting the wrong starting byte changes the key phase. For compression, choosing the wrong wrapper can make a valid stream fail. For cryptography, the key, nonce/IV, range, mode, tag, and any additional authenticated data can all matter.

Outer wrapper, inner content

A firmware download may include vendor headers, compressed filesystems, boot code, applications, and configuration. The outer filename does not tell you the CPU of every member. A package can contain code for several components. First identify the container, then identify each interesting child on its own terms.

  2. Expect a gzip wrapper around a tar archive. Review the entry names, kinds, sizes, and offset provenance.

What did the configuration prove?

A setting named port with value 8080 is stored configuration. It does not prove a listening server starts, which interface it binds, or whether a program actually reads the setting. To establish use, find the consuming executable and follow its parser or references. In this tiny synthetic package, the ARM function does not read that configuration; the separation is intentional.

This is an important firmware habit. Adjacent files are not automatically connected. A service name, certificate, or default setting is a lead. Identify the startup or consuming path before drawing a system-level conclusion.

Real updates can change checks, constants, error paths, dependencies, or data without changing every function. 22. Your first real malware investigation

The harmless cases teach habits you can carry to real samples. Real malware adds uncertainty and consequences, not a new set of magic buttons. Start with static inspection and one narrow question. No part of this chapter requires launching a sample on your device.

Where to get a sample

MalwareBazaar is a research sample database. Its browser supports searches such as sha256:..., file_type:elf, and tags. Record the sample page, exact hash, type, and metadata before downloading. Follow the current download/authentication instructions on the service. Labels are community/engine context, not conclusions from your own analysis. See its FAQ for service details.

If you use a file already collected by an authorized honeypot, preserve its collection time, original hash, and the relevant existing log context. This book does not walk through deploying a honeypot. A downloaded file and a shell command in a log are data to inspect, not instructions for your own terminal.

Keep the file inert

Use the file picker inside SPECTRA to open a sample as data. Do not double-click it to “see what happens,” run its installer, enable document macros, or follow URLs found inside it. Keep downloaded unknown files apart from ordinary documents. A current browser and local analysis reduce some exposure; they do not make hostile parsers or files mathematically risk-free.

Sample downloads may arrive in password-protected archives. Follow the archive's current instructions using an appropriate trusted archive tool; SPECTRA's container inspector does not decrypt encrypted ZIP archives. Do not disable device protections to force a download or run. If your phone/tablet cannot extract the archive safely, continue with the benign lessons and the sample's public metadata. There is no learning requirement to execute live malware.

A complete first-pass worksheet

  1. Identity: Open the extracted member. Compare its SHA-256 with the expected member hash. Record format, CPU, size, entry, and any parse warnings. An archive hash is not the member hash.
  2. Question: Choose one: where is configuration stored, what file path is prepared, or which routine decodes a buffer? Avoid beginning with “identify every capability.”
  3. Structure: Review executable and data regions, imports/symbols, suspicious-looking boundaries, and whether a managed header points toward ILSpy.
  4. Detection: Run DiE if within its cap. Keep the raw report and distinguish heuristic from database evidence.
  5. Strings: Search a small theme: configuration, paths, error messages, or protocol terms. Record exact offsets and encodings. Do not open extracted network indicators.
  6. Context: Follow a reference into Disassembly. Find the surrounding function and its caller. Note unresolved targets and analysis limits.
  7. Reconstruction: Decompile the selected routine. Check the operations supporting your hypothesis against assembly or IL.
  8. Recovery: If code establishes an encoding/key, decode the exact relevant range and preserve provenance. Do not treat an attractive guess as confirmed plaintext.
  9. Optional model: Read debugger preflight before execution. Use a focused supported setup only when you understand inputs and missing state. A static-only finding is a valid result.
  10. Report: Export the project/evidence and write what is known, suspected, and unresolved.

Three platform routes

Windows native PE: use imports, strings, call arguments, native reconstruction, and supported x86/x64 model experiments. A Windows ARM64 PE can be statically analyzed with the appropriate CPU while remaining incompatible with the x86/x64 Windows process model.

Linux ELF: inspect machine, class, byte order, program headers, interpreter/dependencies, symbols, and syscall-related code. An ARM ELF can be statically inspected even when its startup requires unsupported behavior. Zero imports does not equal no dependencies.

Managed .NET: browse types/methods, follow data from entry or a meaningful caller, inspect serialization/crypto/network evidence, and resolve matching local metadata dependencies. Do not select native machine-code emulation as a substitute for a CLR managed debugger.

What a first report can honestly say

“Sample [hash], collected from [source]. The selected function references a file path and passes a buffer to a named write operation. The buffer appears to be produced by this decode routine. The decoder's output was [statically recovered / observed under stated emulation]. Network behavior and persistence were not established by this investigation.” Replace every bracket with evidence or a stated unknown.

Checkpoint: Your chosen sample is packed and the current tools do not expose its inner code. Have you failed? Answer: No. You can document the wrapper, evidence, affected regions, and exact limit reached. Unsupported does not mean harmless, and it does not justify inventing an unpacked result.

24. Save a run, inspect a trace, and know what survived

A trace is an ordered record of observations. It can help you answer which instruction ran before a write, which modeled call returned an error, or how two supplied inputs differed. Its value depends on what was recorded, when capture began and what was left out. A convincing-looking list does not automatically describe the whole execution.

Record the Linux exercise

  1. Save your current investigation. Load the built-in Linux exercise and inspect its virtual stdin, architecture and process-model preflight.
  2. Initialize the session. Before stepping or running, find Persistent recording. Start with the 2 MiB byte budget for this small exercise and choose Start recording.
  3. Run the prepared routine to its expected exit. Inspect the read/write/exit events, output bytes and stop reason. A recording cannot repair missing OS behavior; a stopped unsupported syscall remains a stopped experiment.
  4. Choose Stop recording and wait for the saved/completed status. This flushes the remaining segment. Open the recording for review and inspect its first and last records.
  5. Export the recording, then use Save completed file when the prepared download is available. Confirm the file appears in your device's downloads. Preparing an export is not the same as saving it outside the tab.

Persistent recordings use ordered segments in local browser storage. The chosen byte budget and record/instruction limits bound the recording. They do not promise infinite execution or zero memory use. A killed tab can lose the latest unfinished segment. Browser storage can also be cleared or evicted; an exported file is the portable copy.

Read an observation carefully

For a write, record destination, captured bytes and order. For a register, distinguish a value recorded before an attempt from a final state reported elsewhere. For a model event, name the modeled service and supplied response. A fake virtual file in an exercise is evidence of that experiment, not a disk write on your real device.

The long recording export is newline-delimited JSON: a sequence of records with a required completion footer. A missing footer or interrupted-export status matters. Do not rename a partial download to make it look finished. Retain a completed earlier export or repeat the bounded benign experiment when appropriate. Gaps must remain gaps, not guesses.

Open somebody else's trace

SPECTRA offers two read-only trace slots, search and retained-order comparison. Its compact version-1 trace file contains the latest 200 instruction records plus bounded event/write channels and final mappings. It is not the same as the longer version-2 persistent recording. Check the format and completeness before assuming the start of the file is the start of a process.

Imported observations stay unverified. A valid checksum detects alteration relative to the stored digest; an author could recompute both. It does not establish who recorded the trace or whether their story is true. The import does not initialize an emulator, execute a sample, or turn a record into a time-travel checkpoint.

If the sample hash matches, byte/assembly navigation can connect recorded locations to your open artifact. If it does not match, keep the mismatch visible. The same address in another build can refer to different code. External adapters accept documented subsets, including uncompressed x64dbg v1 traces and bounded Chrome trace JSON, but adapter output is still imported evidence with its original scope.

Compare events, not just row numbers

One run may perform an extra check before reaching a common event. An event-aligned comparison can help find the later correspondence; row 20 versus row 20 need not be the same action. Alignment is bounded and heuristic, so inspect what it matched and the unmatched spans. A matched event label does not prove equal inputs, equal memory or equivalent behavior.

30. From packed bytes to interpreted behavior

A recovered file can contain instructions for another program rather than instructions for your CPU. This is the bridge between Black Loom and Puppet Core. First ask how bytes are stored, then ask who interprets them.

Keep three representations separate

RepresentationThe question it answers
ContainerWhere does the meaningful byte window begin and end on disk?
Recovered image or bytecodeWhat did reconstruction produce, and which offsets belong to that output?
Native interpreterWhich CPU instructions read and implement the custom commands?

In 007 you reconstruct an image, then inspect its code at the supplied base. In 008 the container supplies a virtual program, while interpreter.bin is the native x86-64 code that gives that program meaning. Disassembling every container byte as x86-64 may produce plausible text. That text is not proof those bytes are CPU instructions.

A small mapping exercise

For an unrelated toy container, suppose bytecode starts at file offset 0x30 and its virtual program counter is 0x06. The absolute file offset is 0x36. If those bytes are copied to memory base 0x9000, their virtual-program memory address is 0x9006. Neither number tells you the native interpreter's current instruction address. Write the coordinate system beside every number.

Trace a toy instruction language

Suppose a toy instruction ADD 03 changes an eight-bit accumulator A from fe to 01, then advances virtual PC by two. That is a virtual instruction implemented by several native CPU instructions. A trace row should record the PC before the instruction, its bytes, A before and after, and the next PC. Do not count the native instruction addresses as virtual byte offsets.

Now suppose a virtual compare saves its equality result in a separate variable Z. A native bounds check might change the CPU's own zero flag afterward. The interpreter can still branch using saved Z. In 008 you will locate the register holding that saved virtual flag rather than assuming the most recent native CMP controls every virtual branch.

Know what a failed run means

Use a pair of observations: status and result. A successful run returning zero can mean rejection. A truncated input, unknown instruction or exhausted analysis budget is a different outcome; its result may be unavailable. Record that distinction before discussing acceptance. An analysis error is not evidence that a program rejected an input normally.

Carry this into future research

This habit helps when examining script engines, configuration interpreters and virtualized code. Recover the grammar and state transitions, preserve bounds and provenance, and keep unknown behavior explicit. The teaching interpreter is deliberately small. Its checks do not make it a general-purpose hardened sandbox, and its eight commands do not describe every real interpreter.

34. The vocabulary, without the gatekeeping

ABI
Rules for how compiled pieces cooperate: argument placement, stack alignment, returns, and more. A CPU match alone is not an ABI match.
Address / offset / RVA
An address names a memory location. A file offset names a byte position in a file. A PE RVA is relative to the image base. Always label which one you mean.
API / syscall
An API is an interface offered by software. A syscall is a request into operating-system services. SPECTRA models selected behavior rather than supplying every implementation.
Artifact / provenance
An artifact is the thing being examined. Provenance records where it came from and how it was transformed, including hashes and parent-child relationships.
Basic block / control flow
A block is a straight run of instructions with boundaries at transfers. Control flow is the set of possible paths between them.
Breakpoint / watchpoint
A breakpoint watches execution at an address. A watchpoint watches a memory access. Their pause timing can differ.
Compiler / linker / loader
A compiler translates source into lower-level code. A linker combines code and resolves relationships. A loader maps an executable and prepares entry state.
Decompiler / disassembler
A disassembler decodes instructions from bytes. A decompiler builds a higher-level reconstruction using instructions or managed IL and metadata.
Dependency
Code, data, a runtime, or an external service required by the target. Not every dependency appears in one imports list.
Endianness
The byte order of multi-byte values. It must match the target representation.
Entropy
A statistical measure of byte distribution. It can guide region selection, but it is not a malware score or proof of encryption.
Entry point
The location where a loader begins execution. Startup work may run before the source-level main function.
Hash
A fingerprint of bytes. It identifies an artifact; it does not explain behavior or prove trust.
Heap / stack / BSS
Different memory roles: allocations, call/temporary storage, and zero-initialized data. Some loaded bytes have no stored file counterpart.
Heuristic
A useful rule of thumb that can be wrong. Preserve its evidence and confidence instead of treating the label as proof.
Hook
In this lab, an analyst-supplied replacement for one modeled call boundary. It changes the experiment and must be documented.
Import / export
A requested external symbol versus a symbol exposed for other code to use.
Indirect call
A call whose destination is obtained through a register or memory value rather than fully stated as a fixed target.
Instruction set / ISA
The operations and encodings a CPU family understands. Extensions and modes still matter.
IOC
Indicator of compromise: a contextual clue useful in detecting or investigating malicious activity. A raw string is not automatically an IOC.
Managed / native
Managed code relies on a managed runtime's execution model and metadata. Native code targets machine instructions. Files can contain both.
MMIO
Memory-mapped input/output: accesses to addresses representing hardware registers. A recorded response is not a full device simulation.
Obfuscation / packing
Transformations that make understanding harder, or wrap code/data for later recovery. Legitimate software can use them too.
Pointer
A value interpreted as an address. The pointer and the bytes it points to are different things.
Relocation / load bias
An adjustment to address-dependent data; a load bias is the displacement between linked and loaded locations.
Static / dynamic
Studying stored content versus observing execution. An emulated run is dynamic within its stated model.
Symbol / stripped
A named code/data identity; stripped files have had some helpful metadata removed.
Thunk
A small forwarding or adaptation routine. Follow it to understand the target and any transformation.
Trace / coverage
A record of execution attempts versus a summary of observed locations/transitions. Neither automatically describes all possible paths.
Virtual file
Bytes with a path inside the model. It is not a file written to that path on your real computer.
Xref
Cross-reference: an evidenced relationship between locations. A static xref is not itself a runtime event.
APK / DEX
An Android package and a format holding managed class definitions and bytecode. An APK can also contain resources and native libraries.
Manifest
Structured declarations about an Android app, including components and permissions. A declaration is not an observed action.
TLV
Type, length, value. A record style in which a tag identifies a kind and a length bounds its value; exact widths and length meaning come from the format.
Exclusive end
The first byte after a range. A range starting at 0x20 with length 4 covers 0x20 through 0x23 and ends exclusively at 0x24.
Collision
Different inputs producing the same hash or identifier. Matching a short hash gives candidates, not necessarily unique identity.
Short circuit
An earlier decision ends a path before later checks run. The existence of a later check does not mean every input reaches it.
Modular arithmetic
Arithmetic retaining a fixed width, such as an 8-bit addition keeping only the low eight bits. Carry beyond that width is discarded unless separately used.
Coverage gap
A behavior or class absent from a particular set of observations. Absence from those runs does not prove it is unreachable.
Persistent recording
Ordered observations saved in bounded local segments. It is not automatically a replayable execution state.
Routine history
Supported reconstruction of earlier action boundaries in a bounded x86/x64 bare-routine experiment.
Provenance
Where evidence came from and what transformations, assumptions and identities connect it to the claim.

Offsets 0x10 and 0x48 change. The former is a revision byte. At 0x48, 0x75 (jne) becomes 0x74 (je). Equality now jumps to failure, so 0x5a is rejected and other byte inputs pass. Both jumps target file offset 0x50.

002/01 · Map the relay
SPECTRA{rva_0440}

SPECTRA{glass_signal}

The entry LEA uses RIP after the seven-byte instruction: RVA 0x1007 + 0x1079 = 0x2080. That maps to file offset 0x480, whose string is channel=glass_signal. The other strings are unreferenced decoys.

002/03 · Switchboard
SPECTRA{mode_05}

Bit 2 must be on, bit 3 off, and the low two bits must equal 01. The unique four-bit pattern is 0101 = 0x05. TEST preserves EAX; AND keeps only its lowest two bits.

002/04 · Return path
SPECTRA{call_28}

The helper at VA 0x4020 computes 3*x+7 and returns to main at 0x4007. Main requires 0x7f (127), so x=(127-7)/3=40=0x28. Inequality reaches xor eax,eax; ret.

002/05 · Fractured records
SPECTRA{0023_0056}

Record headers are 0x10, 0x18, 0x23. The third payload starts at 0x26 with declared length 0x30, claiming an exclusive end of 0x56. Only 0x40 bytes exist, so the third record is invalid; 0x16 claimed bytes are missing.

The largest section raw end is .idata: 0x600 + 0x200 = 0x800. CST3 begins there. The 16-byte header puts payload at 0x810; its u16 length is 0x65, ending exactly at file size 0x875. SizeOfImage is not a disk offset.

Repeating XOR with 01 02 03 yields profile=nightjar. The host is telemetry.example.invalid, marker RAVEN7 and mode 0x80. This is reversible obfuscation, not strong encryption. No connection was observed or requested.

The loop processes indexes 0..5. Zero-extended byte values 82, 65, 86, 69, 78, 55 sum to 435 = 0x01b3. After INC makes ECX=6, JB is not taken. Exactly six bytes are read.
