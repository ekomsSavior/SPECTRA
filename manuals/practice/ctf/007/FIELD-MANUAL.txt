STAGE 01 / Bound the packed stream

A container holds a packed byte stream and a footer. Find the exact packed input window as [start,end), using absolute container file offsets. Submit start and EXCLUSIVE end as four hex digits each.

WHY THIS MATTERS

Unpacking begins with a trustworthy input boundary. Feeding header or footer bytes into a decoder can look like a codec failure even when the transform is correct. It also matters for attribution: a recovered output belongs to a specific source window and transform, not merely a filename.

WORKFLOW

Read MEMORY-MAP.txt and FORMAT-NOTES.txt. Open black-loom.blm in SPECTRA Hex explorer. Read the header size at +0x05 and the little-endian packed count at +0x06.

Calculate end = start + packed count. Locate the footer and check that it begins at end, outside the selected stream. A byte length is a count, not an end offset.

Record the packed window separately from expected output length, entry offset and preferred base. Submit only the two container offsets.

DEEPER WALKTHROUGH

Open the container as data. BLM7 identifies the exercise format; it does not turn this into PE or ELF. Follow the provided field layout rather than guessing from strings.

Read the one-byte header count at 0x05. At 0x06 read a little-endian u16: low byte + 256 times high byte. This field counts compressed source bytes, including the end control.

Compute a half-open interval. Its last included byte is end minus one. If you accidentally use the total file size, you will include the human-readable footer after the terminal control.

Create separate columns for container offsets, reconstructed image offsets and virtual addresses. The entry-offset field describes the future output; it is not where payload code begins in the packed file.

Do not infer unpacking success from a readable footer or the apparent entropy of a file. Here we can verify the declared window, transform, output length and output bytes independently.

CHECK YOUR REASONING

Does end minus start equal the packed count, and does the byte at end belong to the footer?

IF YOU GET STUCK

Unknown / Raw binary is expected. Use Hex explorer, not Disassembly, for this header. All flag numbers are hex without 0x; pad offsets to four digits.

FUTURE WORK

When examining an overlay, resource or embedded payload, record the exact source span before attempting decompression. This makes your extraction reproducible.

Flag format: SPECTRA{span_ssss_eeee}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: The header-size byte gives the first packed byte. Read the two-byte packed count low byte first; do not reverse the entire header.

Hint 2: The packed count includes the final 00 control. The first byte of the footer is excluded. A range [0x20,0x30) contains 0x10 bytes, not 0x11.

Hint 3: Keep a ledger: source start = header size; source end = start + packed count. The expected reconstructed size is a different field and does not determine the source end.

STAGE 02 / Recover the token grammar

Study the control classifier, then trace practice-tokens.bin. Find the number of output bytes and the final output byte. Submit both as two-digit hex values. The terminator produces no output.

WHY THIS MATTERS

A packed stream is a sequence of instructions for a data transform. Confusing source bytes with output bytes produces off-by-one errors and false offsets. This small run-length format makes variable-length mapping visible before you encounter more complex codecs.

WORKFLOW

Open loader-code.bin in Disassembly: offset 0x000, length 0x1e (30 decimal), base VA 0xa000, x86-64, Little endian. Click Decode range and select All decoded instructions.

Use FORMAT-NOTES.txt to connect EDX kind and EAX count with literal, repeat and end tokens. Open practice-tokens.bin as data; mark each control byte and its data bytes.

Trace source consumption and output production separately. Count reconstructed bytes, then read the final emitted value. The worksheet is optional after your manual trace.

DEEPER WALKTHROUGH

The classifier is only 30 bytes. MOVZX makes CL an unsigned byte. TEST AL,AL identifies the zero control before the high-bit test. EDX labels the kind; EAX gives a count.

For controls 01 through 7f, the count is the control value. The next count source bytes are literal data. Their values can include 00 or 80; they are not new controls while the literal token is being consumed.

For controls with bit 7 set, mask that bit away and add three. Read one following value and emit it count times. This consumes two source bytes even when it produces a long run.

Work through practice-tokens.bin with two cursors. Advance input by control plus its data bytes; advance output only by the bytes emitted. The 00 control terminates but contributes no output.

This is compression, not encryption. No key is missing. The complete decoder also checks truncation, capacity and end position; the tiny classifier only explains control meaning.

CHECK YOUR REASONING

Can you explain why a repeat token consumes two bytes but can produce more than two?

IF YOU GET STUCK

Byte length is 0x1e, not 0x30. Do not disassemble the practice stream. If your count includes the final 00, remove the terminator from the output ledger.

FUTURE WORK

Recognizing token boundaries helps reconstruct custom packers and distinguish compressed streams from ordinary strings or instruction bytes.

Flag format: SPECTRA{trace_nn_bb}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: The routine reads CL without sign extension. Zero ends. A high bit of zero selects literal; a high bit of one selects repeat.

Hint 2: For repeat controls, count = (control AND 7f) + 3. Only one source value byte follows, regardless of the output count. Literal controls consume count following bytes.

Hint 3: An unrelated example: 02 48 49 80 2e 00 emits HI... . Its output length is 05 and final byte 2e. Apply the same ledger to the provided practice input.

WHY THIS MATTERS

Recovered bytes become useful evidence only when you know how they were produced. A successful decoder return, exact length and matching digest provide different checks. Opening the output as a new sample also prevents you from interpreting compressed data as payload instructions.

WORKFLOW

DEEPER WALKTHROUGH

The helper shows each token with input offset, input bytes consumed, output offset and output count. Compare the beginning with a manual trace. It never executes the image and does not upload the selected file.

Success requires a final end token at the selected input boundary and exactly the declared output size. A partial decode is not enough. The download remains disabled if either check fails.

Now open the reconstructed file as the main SPECTRA sample. Use the entry offset as a file coordinate. Read four raw bytes from that location; the next stages explain how that entry relates to memory and code.

STAGE 04 / Rebase the evidence

The same recovered image is captured at a different base. Compare memory-decoded.bin with memory-rebased.bin. Find the base delta and the new QWORD pointer value. Submit each as eight hex digits.

WHY THIS MATTERS

Memory dumps often differ from disk or pre-load images because addresses were relocated. Calling every byte difference a malicious patch is a mistake. You need to distinguish instruction location, pointer storage and pointer target.

WORKFLOW

Open memory-decoded.bin as the main file. In Binary diff, load memory-rebased.bin as the second file and Compare. Use the raw byte comparison table; an empty matched-functions table does not block this task.

Inspect the complete eight-byte slot at image offset 0x18 in Hex explorer for each snapshot. Read it as little-endian QWORD. Calculate actual base minus preferred base from MEMORY-MAP.txt.

Check that new pointer = old pointer + delta and that subtracting each base gives the same data offset. Decode the payload with the matching map row to see why its RIP-relative bytes stay unchanged.

DEEPER WALKTHROUGH

SPECTRA Binary diff can identify changed raw bytes even without automatic function matching. Keep the before and after filenames straight. Both snapshots contain the same 256-byte logical image.

Read all eight bytes at offset 0x18. It is a 64-bit pointer even though the exercise values fit into eight hex digits. A one-byte diff is merely how this particular address adjustment appears in its encoding.

Compute delta = actual base - preferred base. Add that delta to the old absolute pointer. Then normalize both pointers by subtracting their respective image base: both should identify data offset 0xc0.

At entry, MOV RDX,[RIP+displacement] accesses the pointer slot. RIP for this addressing calculation is the next instruction address. When both instruction and slot move by the same amount, their relative displacement does not change.

The snapshots were authored with one relocation slot. This models a relocation concept, not a full PE relocation directory. Other formats, relocations and outside-image pointers require their own rules.

CHECK YOUR REASONING

Can you name three different coordinates: slot file offset, slot VA and the VA stored in the slot?

IF YOU GET STUCK

Use the raw byte table rather than waiting for matched functions. The pointer is not the instruction address. Keep leading zeros in the eight-digit flag fields.

FUTURE WORK

Normalize load addresses before comparing captures so relocation changes do not drown out actual code or configuration changes.

Flag format: SPECTRA{rebase_dddddddd_pppppppp}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: Compare the same image before and after the documented base adjustment. The raw diff may show just one changed byte inside an eight-byte pointer.

Hint 2: For a little-endian QWORD, the first byte is least significant. The slot address and the value stored in that slot are different things.

Hint 3: Relative distances within the image stay fixed when the whole image moves. The RIP-relative instruction finds the slot; the absolute value in the slot must point into the image at its new base.

STAGE 05 / Follow the handoff

A small handoff receives validated inputs and transfers control into the rebuilt image. Find the destination VA and whether the transfer uses JMP or CALL. Submit an eight-digit VA followed by jmp or call.

WHY THIS MATTERS

Recovering bytes is not the same as proving those bytes receive control. A transfer calculation connects reconstruction to execution evidence. Understanding a tail jump also prevents incorrect call-stack and function-boundary assumptions.

WORKFLOW

Open loader-code.bin in Disassembly: offset 0x200, length 0x07 (7 decimal), base VA 0xa200, x86-64, Little endian. Decode range and select All decoded instructions.

Use the handoff register capture in OBSERVATIONS.json: EDX is the entry offset, R8 is the actual image base, and RCX is the payload index. Follow MOV, ADD, then the transfer instruction.

Convert the computed destination VA back to an image offset and confirm it reaches the payload row in MEMORY-MAP.txt. Compare with the captured instruction-address sequence.

DEEPER WALKTHROUGH

These seven bytes are a teaching component. The caller contract says decoding, size, relocation and entry range were already validated. The snippet does not perform those checks itself.

The captured EDX is an offset within the image, not a VA. On x86-64, writing EAX zeroes the upper half of RAX. Adding R8 then produces the absolute target for this capture.

Read the actual indirect transfer instruction. Its operand is the calculated register. Do not classify it from what you expect a loader to do.

The provided trace records executed instruction addresses in an isolated CPU model. Locate the computed destination after the handoff instructions. This proves that target was reached for the listed inputs only.

Convert the target back to image offset by subtracting actual base. This should point at the recovered routine, not the pointer slot or data table. No native execution is necessary to complete the exercise.

CHECK YOUR REASONING

Could you explain why the handoff adds a base to an offset, but must not add the base again to an existing absolute VA?

IF YOU GET STUCK

Use length 0x07, not the rest of loader-code.bin. If your target is 0x6000c0, you followed the data pointer instead of the entry field.

FUTURE WORK

When analyzing unpackers, document where control actually goes and which observations support it. A plausible entry is a hypothesis until static or trace evidence connects it.

Flag format: SPECTRA{handoff_vvvvvvvv_kind}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: MOV EAX,EDX copies the entry offset and zero-extends it into RAX. ADD RAX,R8 combines it with the actual base.

Hint 2: The QWORD data pointer from stage 04 is not the entry. Entry offset and data offset serve different purposes.

Hint 3: A JMP changes instruction pointer without pushing a new return address. A CALL would push one. Here the payload eventually returns using the existing harness return address.

STAGE 06 / Read the signed data

Analyze the rebuilt payload for indices 1 and 2. Determine its two return values. Submit each as two hex digits in index order. Interpret the table bytes using the instruction that loads them.

WHY THIS MATTERS

Hex displays bytes without deciding their meaning. The load width, extension and branch determine how code interprets them. After reconstruction, you still need ordinary data-flow analysis rather than treating an unpacked artifact as the end of the investigation.

WORKFLOW

Open memory-rebased.bin in Disassembly: offset 0x040, length 0x19 (25 decimal), base VA 0x600040, x86-64, Little endian. Decode range; select All decoded instructions.

Follow the pointer load, then MOVSX EAX,byte [RDX+RCX]. Read table bytes at file offset 0xc0 in Hex explorer. Index 1 means the second byte; index 2 means the third.

Trace TEST, JS and the selected arithmetic for each input. Note the signed value before NEG and the final EAX. The observations provide one check, not both answers.

DEEPER WALKTHROUGH

Follow the first instruction to the pointer slot, then read the target data. The pointer is already adjusted in this snapshot. A file-offset view and a memory-address view must refer to the same bytes.

RCX is a zero-based index under the caller contract 0..3. At table offset 0xc0, add the index to select one byte. The routine does not enforce that bound itself.

MOVSX copies the sign bit into the higher bits of EAX. Convert a byte with its high bit set by subtracting 256. This is different from MOVZX, which fills high bits with zeros.

TEST EAX,EAX does not change the value. JS follows the negative result to NEG and ADD 0x40. The other path adds 0x20. Trace the path selected by each input, not both branches in sequence.

Compare your index-2 return with the bounded handoff trace. A match supports your interpretation for that input. It does not prove every possible index is valid or characterize an actual malware family.

CHECK YOUR REASONING

Would replacing MOVSX with MOVZX preserve the result for these two bytes? Explain the changed branch.

IF YOU GET STUCK

Base VA is the VA of the first decoded byte, 0x600040, not 0x600000. Length 0x19 is 25 decimal here; do not reuse 0x13 from CTF 001. Keep the flag to two bytes, not sign-extended register dumps.

FUTURE WORK

Signedness mistakes are common in parsers, counters and recovered structures. Let instructions and contracts determine the interpretation, then test boundary values.

Flag format: SPECTRA{returns_aa_bb}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: MOVSX sign-extends a byte. Values 80..ff represent -128..-1, not 128..255, in this calculation.

Hint 2: TEST EAX,EAX sets the sign flag from the 32-bit result. JS takes the negative path. NEG changes its sign; the following ADD still applies.

Hint 3: For an unrelated table byte fd, signed value is -3. NEG makes 3, then adding 40 hex yields 43. Apply that path to the two requested table entries.

STAGE 07 / Reject the partial result

A truncated stream writes some bytes and then fails. Find the number of bytes actually written and the EAX return status. Submit a two-digit write count and an eight-digit status. Do not count untouched destination bytes.

WHY THIS MATTERS

A failed transform may leave convincing output in memory. Treating partial writes as a valid image can send an investigation in the wrong direction. The return contract, output bounds and caller decision are as important as the bytes themselves.

WORKFLOW

Open broken-tokens.bin in Hex explorer and trace it with the grammar. In the Reconstruction worksheet select offset 0, length 2, expected output 8. Observe the failed result and disabled download.

Read broken_decode in OBSERVATIONS.json. Compare its recorded writes with the initial a5 sentinel and final destination. Count bytes written, not buffer capacity.

For the reference path, decode loader-code.bin at offset 0x080, length 0x82 (130 decimal), base VA 0xa080, x86-64, Little endian. Follow source exhaustion to the failure return.

DEEPER WALKTHROUGH

The broken stream contains one repeat control and its value, so that token can be processed. The missing piece is a terminal control after it. Source exhaustion is not defined as implicit success.

The reference decoder checks bounds before writing each current token. That prevents the failing token from overrunning its buffer, but it does not roll back earlier complete tokens.

OBSERVATIONS records the initial output sentinel, actual byte-write events and final output. Count the writes. Do not interpret the entire eight-byte capture as produced output.

The EAX failure sentinel is separate from the number of bytes already written. The worksheet displays that distinction and disables downloading a failed reconstruction. The caller must discard or separately label partial output.

The supplied CPU trace ends at the failure return. It never jumps into the partial output. A real analysis should likewise distinguish evidence of writes from evidence of successful loading or execution.

CHECK YOUR REASONING

Can you explain how a nonempty output buffer and a failed decoder return can both be true?

IF YOU GET STUCK

Expected output 8 is a capacity/validation input, not the answer. Do not count a5 sentinel bytes. The worksheet may describe the cause in words; the assembly return status is in the contract and trace.

FUTURE WORK

Check API and parser error semantics when reconstructing memory. Preserve partial artifacts with an explicit failure label instead of treating them as completed payloads.

Flag format: SPECTRA{partial_nn_ssssssss}

Enter only the full SPECTRA{...} flag. Use lowercase hex, no 0x prefixes, and no text after the closing brace.

Hint 1: The first token is a complete repeat token. After it, the input has no remaining byte from which to read an end control.

Hint 2: Earlier writes are not undone when a later check fails. A5 in the tail was initialized by the harness; it was not emitted by the decoder.

Hint 3: The contract returns ffffffff on error, regardless of the number of earlier output bytes. Use the write records to find the separate count; no handoff is valid after this failure.

STAGE 08 / Write the reconstruction report

WHY THIS MATTERS

WORKFLOW

DEEPER WALKTHROUGH
