# iPad / iPhone Safari acceptance route — v0.16

Status: **user-reported iPad and phone pass, 18 October 2026** (“all is well”). Device models/OS and individual route results were not supplied. This report clears the earlier hold on backlog work; it does not establish a separate VoiceOver or measured total-memory pass. The route below remains available for reproducible follow-up. Desktop Chromium checks are separate. Use the built-in benign decoder; no malware or extra software is needed. Record device model, iOS/iPadOS version, Safari version if shown, normal/private mode, and which step fails. Start in normal browsing, with a few other tabs closed. Private mode is a separate test because persistence can differ.

1. Open `https://spectra.churchofmalware.org/?v=0.16#lessons`. Confirm v0.16 in the sidebar. On a narrow screen, use the navigation menu.
2. Training ground → **Load the decoding exercise** → **Replace with exercise** if prompted. In Debugger lab, **Initialize session**. Initialization should not execute instructions.
3. In **Persistent recording**, use **2 MiB** / **1,000 instructions**, then **Start recording**. Return to the stepping controls and **Run / continue** (1,000 budget). The benign loop should return after roughly 221 instructions. **Stop recording**. Expect 221 instruction observations plus the initial mapping/stop observations, with no reported retention gap.
4. Use **Show scratch**, then **Send memory to Recovery lab** with 256 bytes. Expect `https://decoded.example/config` in the captured data. It is a reserved example hostname; the demo does not contact it.
5. File structure → **Mapping source: Captured debugger mappings**, **Input space: Virtual address**, Location `0x100000` → **Resolve address**. Expect original file offset `0x0`. Try `0x60000000`; scratch is allocated memory, so no original offset should be invented.
6. Notebook → write your own explanation in **Case notes**, at least 40 characters: the scratch address, the decoded URL, and why a URL does not prove a network request. In **Selective evidence bundle**, keep findings and select **Original sample bytes**, **Captured/imported traces and opened recordings**, and **Lesson evidence checklist**. Select recovered bytes too if you want the captured layer preserved. Leave unrelated groups unchecked. **Prepare inclusion inventory**; inspect names, sizes and hashes.
7. Training ground → **Check my evidence**. Expect **6 / 6**. Follow one of the “Go to…” buttons and come back. **Save lesson workspace** and wait for a saved time. Reload the tab, go to Training ground → **Resume saved workspace**. All six milestones should remain, marked **historical / imported**. No sample instructions should run on restore.
8. Debugger lab → Persistent recording → choose the saved recording → **Export recording** → **Save completed file**. Confirm `spectra-recording.ndjson` appears in Safari Downloads / Files. Then **Import recording**, choose SPECTRA format, select that file in Files. It should open as **Imported observations; unverified**, retaining order and count. Search `xor`, inspect a row, and try Mapping at selected event on a local-SPECTRA recording. Do not expect reverse execution.
9. Notebook → **Prepare inclusion inventory** again to include the latest progress → **Download prepared bundle** → **Save completed file**. Confirm the ZIP exists in Files. **Open evidence bundle**, select it, review the verified inventory, then deliberately **Replace workspace with reviewed evidence**. Confirm notes, sample identity, selected recording and six historical milestones survive. Unselected payload groups must remain absent.
10. Repeat a preparation/export and tap **Cancel preparation / export** while it is running. A small fixture may finish too quickly; note that instead of calling it a cancellation pass. No new completed-file link should appear for an interrupted write. Use **Discard prepared files / clear old export leftovers** when finished; saved investigations/recordings should remain.

## Larger-file and eviction checks

After the small route succeeds, a tester may repeat with their own benign 8 MiB then 24 MiB file and selected sample-only evidence. Note elapsed preparation/save/import times and any tab reload/crash. Try 64 MiB only if earlier runs remain comfortable. Safari does not expose a reliable page-level total-memory meter; do not invent a peak-memory figure from a viewport or desktop JS heap. Record observable tab stability and, if available, device-level instrumentation separately.

Finally export a small completed file, background the tab, return/reload and restore. This checks recovery from a lost session, not a promise that iOS retains browser storage forever. Send device details, steps completed, exact failure text, file sizes and whether Files saved the outputs. No sample contents need to be shared.
